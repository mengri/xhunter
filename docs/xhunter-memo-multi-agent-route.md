# 备忘录：多 agent 路线（备查，未采纳）

## 0. 这份文档的性质

- **不是规范**。规范以 `docs/` 的四份治理文档为准（产品设计 / 使用手册 / 架构设计 / 状态）。
- 记的是**结论与依据**，不是讨论过程：① 为什么不采纳这条路线；② 若将来要做，落点在哪、当前代码缺什么。目的是让同一议题不必被重新讨论一遍。
- 触发重读的条件见 §7。

---

## 1. 议题

**V（评估接口）层怎么补**——「你怎么知道做对了」。

Xhunter 的 V 层长期是空的：今天「任务做完了」的唯一判据是「模型某一轮没发起工具调用」。补它有两条成本结构完全不同的路。

---

## 2. 两条路对比

| 维度 | 判据路线 | 多 agent 路线（对抗性验证） |
|---|---|---|
| 做法 | 门禁（`gates.yml` 具名条目）＋ 结构检查（`ParseOK` ＋ 改动区间封闭在符号内） | 派一个专门挑错的 agent 去审核结果，把它的意见作为结论 |
| 产出性质 | **可执行的证据**（命令跑没跑、输出是什么、语法是否自洽） | 另一个模型的**判断** |
| 可复现性 | 同一份改动两次跑同一门禁，结论相同 | 同一份改动两次评审，结论可能不同 |
| 成本 | 门禁本身的执行时间（结果按内容指纹缓存） | token × N，且不确定性一起放大 |
| 落点 | 现有骨架内：`hunt/gate` ＋ `Session.structuralJudge`（三态判据） | 原语的实现细节（见 §4） |
| 对 `harness` 的影响 | 无 | **无**（这一点曾被误判，见 §4） |
| 与产品定调的关系 | 一致——「判据必须是可执行的证据」 | 相反——它给的仍是判断 |

---

## 3. 决策（2026-09-23）

**走判据路线。** 落点：产品设计 §1.2「判据优先于偏好」、架构 §7.8（门禁规格）与 §6.3 L6（结构检查）。

理由只有一条，但它是硬的：**产品设计 §1.2 要求判据「必须是可执行的证据」，而多 agent 的输出不满足「可执行」，也不满足「可复现」。** 无人 review 的终局要的是「谁来看都不会翻案」，不是「另一个模型觉得还行」。判断可以补充证据，但不能替代证据。

推论的边界：**判据路线有它覆盖不到的东西**——门禁与结构检查都过了、交付仍有系统性缺陷（跨文件一致性、需求理解偏差）。那不是这条路线没做好，是它的能力边界（见 §7）。

---

## 4. 不采纳 ≠ 不可做：若将来要做，落点在哪

**结论：多 agent 编排是「操作原语」，不是 `harness` 的新编排维度。`harness` 一行都不用改。**

依据（都是现有代码的事实，不是设想）：

1. `harness.Engine` 只从流里收 `turn.Text` / `turn.Calls`，**不执行**（IA-1.8）；执行落在业务侧的 `Session.OnTurn`。
2. 因此「派子 agent」完全可以是一个原语的内部行为：`Execute` 里再跑一次 `harness.New(...).Run(...)`，把结果作为自己的 `Result` 返回。对父循环来说，这只是一次普通的工具调用。
3. 子运行用**同一个 `harness`、另一套 handler**（不提交、不落材料、不发终态，只把结果回给父）——这恰好是 `harness` 复用叙事的正面用法：「换一套 handler，就是换一套业务」。
4. 原语的构造参数本来就是**运行期产物**（`workspace` 就是这么传进来的），所以把 `provider` 一并交给原语工厂（`defaultTools(ws, ex, provider)`）是装配层的常规改动。

**这条边界现在是硬的**：装配层只把 provider 交给原语工厂，`harness` 不认识「子任务」这个概念。

**为什么不把它做成 `harness` 的维度**（守住边界的三条代价）：

- 复用叙事崩塌——`harness` 的包注释写着「可被任何『模型调用工具』的产品复用」；一旦它认识子任务，就变成「agent 编排框架」，那句话不再成立。
- 预算 / 取消 / 事件的语义要在 `harness` 里再定义一遍（谁承担子运行的 token、子运行的事件怎么标识、取消怎么逐层传播）。
- 三组 handler 的签名会被迫携带编排概念，`harness` 与 `hunt` 的解耦随之失效。

## 5. 若真要做的缺口清单（按当前代码的实测结论）

| # | 缺口 | 现状（事实） | 最小改法 | 触及层 |
|---|---|---|---|---|
| 1 | **用量回流** | 子运行的 token 只在它自己的 `harness.Outcome.Usage` 里；父运行的 `run.Usage` 只累加**自己那一轮**的 provider 事件 → 子 agent 的消耗**不进父预算** | `hunt.Result` 加 `Usage llm.Usage`，`Session.charge` 把它一并转交策略 | `hunt` 契约（**不动 harness**） |
| 2 | **事件嵌套标识** | 信封只有 `type` / `bounty_id` / `trace_id` / `ts`，子运行的事件与父的混在一条 stdout 流里，无法区分 | 信封加 `parent_call_id`（或 `span_id`）——外部契约**只增不改** | 装配层 `sink` 载荷 |
| 3 | **取消传播** | 已成立：子原语拿同一个 `ctx`，父取消即子取消 | 无需改 | — |
| 4 | **递归上限** | 没有：原语可以无限派下去 | 派发原语自带深度上限（构造参数），并在 `Facts` 或原语状态里数深度 | `hunt` 原语内部 |
| 5 | **预算分摊** | 父的三重预算（token / 轮数 / 墙钟）是**全局水位**，子运行共享 | 共享即最保守，可接受；要分摊就得给策略加「配额」概念——**不做** | — |
| 6 | **写操作的合并** | 子运行若与父**共享工作区**，`Committer` 已统一记账，天然合并；若用独立工作区，需另定合并语义 | 优先共享工作区 | `hunt` 层 |
| 7 | **子 agent 的工具面** | 工具面**在同一构建版本内恒定**（AC-26）：环境能力不决定注册、同一构建内工具名与 schema 不增减；但**工具面随能力接入而扩展**（未实现且不在本次构建范围内的原语不注册） | 若子 agent 需要一份**与父不同**的工具面，那与「同一构建内工具面恒定」**直接冲突**，必须先解决这个设计冲突 | 设计决策（**先于编码**） |

> 第 7 条是最容易被忽略、也最硬的：**「同一构建内工具面恒定」是已承诺的对外契约**（环境能力不决定注册），而「按 agent 角色给不同工具面」会打破它。做多 agent 之前必须先回答这个问题。

---

## 6. 与「判据路线」的关系

两条路不是互斥的终局，优先级是明确的：

- 判据路线是**基线**——它给出可复现的证据，是无人值守能成立的前提。
- 多 agent 只在**判据覆盖不到的地方**才有意义（§7），且它自己也需要判据来兜底（否则「第二个模型说行」就成了新的不可复现判据）。

---

## 7. 什么时候回来读这份备忘

满足任一条才值得重新评估：

1. **出现判据路线覆盖不到的系统性失败模式**：门禁与结构检查都过了，交付仍在评审时被否，且失败可归因于「跨文件一致性」「需求理解偏差」这类无法用命令表达的判据。
2. **平台侧明确要求「第二意见」**，且明确接受「结论不可复现」这个代价。
3. **引入的判据无法在本进程内表达**（例如必须由独立环境、独立依赖树的进程给出结论）——那时它更接近「扩展」而不是「多 agent」，应重新按 §7.7 的 `ExtHost` 评估。

在此之前，本备忘的结论是：**不做**。
