# Xhunter 产品设计

## 0. 文档定位

- 本文定义 Xhunter 的**产品边界与功能需求**：解决什么问题、明确不做什么、具备哪些能力、如何验收、如何分期。
- 实现结构（分层、组件规格、控制流时序、接口验收）见 `xhunter-architecture.md`；使用与集成方式（CLI、Bounty、事件流、结果文件、退出码）见 `xhunter-usage.md`。
- 基线假设：Xhunter 作为**平台侧 executor** 被调度运行，**不存在任何面向人类的交互界面**（无 TUI、无 Web UI、无审批弹窗、无多轮追问）。
- 平台范围：**一期仅支持 linux/amd64（单目标）**。跨平台（NFR-6）保留为架构约束，但不在一期验收范围内；一期实现**不得引入平台相关假设**（路径分隔符、大小写敏感、换行、信号语义等一律按可移植方式处理），以保证后续兑现跨平台时不需要返工。
- 编号规则：`FR-x` 功能需求，`NFR-x` 非功能需求，`AC-x` 验收标准。编号用于跨文档引用，不建议重排。
- 验收环境：一期在 **linux/amd64** 上执行（见 §7）。

### 0.1 命名与术语

命名体系取自 Tavern 的酒馆 + 猎手世界观：**告示板上挂着悬赏令，猎手接单出门，办完回来交差。**

| 术语 | 含义 | 使用范围 |
|---|---|---|
| **Tavern** | 平台 | 已有 |
| **Xhunter** | 本系统的执行体（即本文档描述的对象） | 产品名与文档写作 `Xhunter`；二进制与包名写作 `xhunter` |
| **Harness** | Xhunter 内部的控制循环层 | 架构层名 |
| **Bounty** | 一次任务的委托（任务描述、工作区、预算、策略） | 取代原"任务文件"的说法 |
| **a Hunt** | 一次执行（一个进程的生命周期） | 取代原"运行"的说法 |
| **Session** | 同一会话的执行记录（写操作序列与上下文），可跨机器**续跑**（检查点恢复） | 会话可与多次投递（bounty）关联：同一 `session_id` 下的多次投递**共享记忆与分支**；不传时本次自成新会话 |
| **提示词插件** | 构造首轮 system / user 两段正文的扩展点：**多个插件按装配顺序拼接**（FR-7.8） | 正文由插件给；内核只保留两段的位置与顺序、取一次冻结、内核条款不可覆盖 |

**命名规范（强制）**：产品名 `Xhunter`（X 大写、h 小写，不写作 `XHunter`）；二进制名、包名、环境变量一律全小写，环境变量前缀 `XHUNTER_*`。跨平台大小写敏感度不同（Linux 敏感、Windows 不敏感），必须一次性定死。

**X 的语义**：读作 **cross（跨）** —— 对应"跨机器、跨 runtime 的 failover"，与「智能体不绑机器」的核心设计一致。

**三层隐喻**（仅用于文档与沟通，不进代码）：

| 隐喻 | 对应 |
|---|---|
| 马（有力量、无方向） | 模型 / LLM |
| 挽具与缰绳（把力量导向目标） | Harness —— 工具调度、上下文组装、权限应答 |
| 骑手（决定去哪、做什么） | Xhunter —— 任务执行策略 |

推论：**换马不换挽具** —— 更换模型或供应商不需要改动 Harness。

## 1. 目标与背景

### 1.1 要解决的问题

在无人值守的场景下，把"一个自然语言任务描述"稳定地转化为"一份可应用的代码变更"，并让平台侧能够远程判断它到底成功、失败还是卡住。

### 1.2 设计原则

| 原则 | 含义 |
|---|---|
| **无人类原则** | 任何"等待人类输入"的路径都是缺陷，不是降级策略。所有决策必须由策略引擎预先裁定 |
| **显式失败原则** | 宁可明确失败，也不允许静默成功。所有失败必须显式、可分类、可远程诊断 |
| **只碰必要字节原则** | 变更范围必须收敛到最小，不产生无关噪音。这是 patch 可 review 的前提 |
| **语言中立原则** | 任务的受理与执行**不以开发语言为条件**。核心保持语言无关，符号级能力以**扩展**形式外挂；扩展缺失或语言未注册时自动降级为文本模式，任务照常执行而非被拒绝 |

### 1.3 非目标（明确不做）

| 不做 | 原因 |
|---|---|
| 交互式界面 / TUI / 进度可视化 | 无人类消费者 |
| 多轮澄清提问、审批弹窗 | 无人类可问，且会成为死锁源 |
| 任意命令执行（通用 bash 工具） | 权限面过大，与本设计的安全边界冲突 |
| 测试运行与长时间构建（除门禁外） | 越出"生成代码"的职责边界 |
| 部署、发布、合并决策 | 交付止于**任务分支上的提交**（FR-6.1）；合并与发布归平台侧 |
| 任务分支之外的版本控制写操作 | 不改历史、不 force push、不删分支、不操作其他分支（FR-8.3） |
| 多模态输入输出 | 与编码任务无关 |
| 交互式恢复 UI / 跨 Bounty 会话语义 | 确定性 resume（**检查点恢复**，不重放写操作）属 In Scope（FR-12.1），但无界面、无人工介入；恢复只发生在同一 Bounty 的重派 |

|---|---|

## 3. 运行模型

- **一个进程 = 一个 Bounty = 一次 Hunt**。进程启动即开始，进程退出即终结，不提供进程内复用与跨任务会话。
- **一个任务一个独立分支，分支由 Xhunter 创建并推送**：启动阶段（**任何模型推理与任何写操作之前**）在基线 commit 上创建任务分支并推送，把基线**钉在远端**；交付阶段把改动作为提交推送到同一分支。**这两件事都由 Harness 在固定阶段执行，不由模型驱动**——工具面不含任何 git 操作，模型既看不见也改不了分支名、推送目标与提交内容（INV-11）。分支一旦建立，resume / failover / 交付全部走分支，不再有"基线可获取性"问题。**推送目标只能是 Bounty 指定的任务分支**（FR-8.3）。
- **Xhunter 只针对 git 仓库操作，不依赖 local 工作目录**。投递必须给出仓库信息（远端 + 基线 commit + **任务分支名**）；**是否延续既有会话由"是否给出 `XHUNTER_SESSION_ID`"决定**（见 FR-12.1）。
- **投递而非拉取（Xhunter 侧）**：**Xhunter 不主动联系平台**。一次投递由平台交给进程（命令行给任务正文，环境变量给仓库与模型接入，FR-1.1）；**pull 留在平台侧**——由平台的调度器（如 Tavern daemon）拉取任务、再投递给具体机器。若平台希望"主动领取"语义，应由平台侧 sidecar 实现，Xhunter 保持不变。
- **任务活跃度挂在 Bounty 上，不挂在 runtime 上**。心跳必须按 Bounty **输出**（外部事件通道 = stdout，见 FR-1.4），与 runtime 心跳解耦——否则承载它的机器崩溃时，该任务会永久停留在运行中状态。
- **交付物是任务分支上的提交链**，不是"改动后的工作树"这个中间态。规则（保证线性、可复盘）：
  1. **阶段性提交**：按**任务配置的检查点策略**（FR-1.3c）提交并推送，分支 tip 随任务推进而前进；**交付 = 分支 tip**。提交内容 = **本轮已应用的改动**（工具已在同一轮的响应处理段执行完毕）。两条不变量与策略无关：**无新写操作不提交**、**收尾必提交**；
  2. **只允许 fast-forward 推送**：远端 tip 必须是本地父提交，**绝不 force push、绝不改写已推送历史**（FR-8.3）；
  3. 同时产出**相对基线的整体 diff** 作为附带产物，供 review 与平台展示（FR-6.1）；该 diff **排除会话材料路径**（`.xhunter/**`）。
- **恢复靠检查点而非重放**：崩溃后重派时 checkout 分支 tip（最后一个检查点）即为工作区状态，再读回会话材料继续推理。**不再重放写操作**——检查点之间的改动由模型在下一轮自然重做（代价是有界的：最多一轮）。
- **同一 Bounty 不并行执行**：一任务一分支一进程。材料按 `.xhunter/<session_id>/` 隔离，故**多任务并行同一仓库互不干扰**；若平台违规并行同一 Bounty，两端的 fast-forward 推送会**显式失败**（环境错误），不会静默产生分叉或覆盖。

## 4. 功能需求

### FR-1 任务生命周期与进程契约

| 编号 | 需求 |
|---|---|
| FR-1.1 | **投递形态：任务内容与部署事实分离**。命令行参数给出**任务正文文件路径**（只含任务描述，含验收标准）；**仓库事实（远端地址 + 任务分支 + 基线 commit）与模型接入由环境变量给出**（`XHUNTER_*`），因此同一台机器上跑多个任务不必重复声明部署信息。字段清单与缺省值见 `xhunter-usage.md` §3 |
| FR-1.2 | 启动后从环境变量读取凭据，不读取本地凭据文件。凭据需具备**推送任务分支的写权限**（只读凭据无法完成交付） |
| FR-1.3 | 启动时获取基线：clone/fetch 仓库 → 校验基线 commit（`XHUNTER_REPO_BASE_COMMIT`）可达（按 SHA 浅克隆；不可得时退化为完整克隆）→ **在基线 commit 上创建任务分支并推送**（把基线钉在远端；分支已存在且 tip 为基线或其后代 → 视为续跑，幂等成功；否则环境错误）→ checkout。**本步骤属初始化，先于任何模型推理与任何写操作**；工作区必须干净 |
| FR-1.3b | **阶段性提交（检查点）**：提交累积自上一个检查点以来的全部改动，因此单次失败可在下一轮自愈；**连续失败达上限（默认 3 次）即环境错误**，避免远端不可用时空跑全程。**只允许 fast-forward 推送**（FR-8.3）。密度由 FR-1.3c 决定 |
| FR-1.3c | **检查点触发优先级 + 时间语义**：工具执行统一在**流结束后**（运行段 L5 响应处理），每轮**单一提交点在轮收敛（L6）**，**提交内容 = 本轮已应用的改动**（工具已执行完毕）。优先级：<br>① **门禁通过**（本轮 `check` 通过 → 轮收敛必提交，FR-5.2c）<br>② 模型显式 `checkpoint`（语义声明）<br>③ 结构检查通过（语法级自洽，FR-1.3d）<br>④ 轮边界兜底（判据不可用时）<br>唯一例外：**`every_write` 模式在 L5 逐写提交**（最密档，显式配置才启用）。`on_structure` 为默认模式；`every_turn`/`interval:N`/`final_only` 可显式覆盖。两条不变量与策略无关：**无新写操作不提交**、**收尾必提交**。完整时序见 `xhunter-architecture.md` §6 |
| FR-1.3d | **结构检查（自动判定，不依赖模型自报）**：判据为 ① 目标文件**语法完整**（`ParseOK`）；② 单次编辑的字节区间**封闭在某个符号范围内**（需扩展提供符号范围，M2 起可用）。`ParseOK` 由 false 转 true 表示刚补全了一段代码；区间封闭表示"完整写完/替换了一个方法"。**判据是必要不充分的**：只识别"结构完整点"，不识别"功能完成"，语义完成仍由模型判断（FR-1.3c 的模型 `checkpoint`）。<br>**三态判定，"不可判定"与"未完成"必须分开**：<br>· **通过** → 提交（检查点落在"写完一个方法"这类结构边界上）<br>· **可用但未通过**（存在语法残缺）→ **不提交**，等下一个结构完整点<br>· **不可判定**（语言未注册 / 本轮改动文件数超过上限）→ **按轮兜底提交**——不可判定不等于未完成，否则未注册语言的仓库永远只在收尾提交一次，那是能力损失而非保守 |
| FR-1.4 | 全流程 stdout 输出结构化事件流，stdout 不允许出现非事件内容 |
| FR-1.5 | 结束时写出结果文件（状态、patch 路径、用量、错误、假设清单、**session 增量**） |
| FR-1.6 | 通过退出码表达可分类的终态（见 `xhunter-usage.md` §7） |
| FR-1.7 | 收到 SIGTERM 后停止发起新的模型调用与工具调用，落盘当前状态与已有变更（含 session 增量），然后以被取消状态退出 |
| FR-1.8 | **流程由配置组装**：控制流程不写死在代码里，而是由一份**环节清单**组装——`pre`（初始化）/ `turn.guards`（每轮守卫）/ `turn.steps`（每轮步骤）/ `post`（收尾），可由 Bounty 的 `pipeline` 字段覆盖。**组装结果必须在启动期通过不变量校验**，非法编排直接拒绝（退出码 2）；零值/缺省即默认编排，**行为与不写配置时完全一致**。默认编排见 `xhunter-architecture.md` §4 与 §6 |
| FR-1.9 | **支持多形态驱动，且校验共用**：核心可被①**配置驱动**（外部生成 Bounty/`pipeline` 并投递）②**观察驱动**（外部消费事件流做展示）③**单步驱动**（进程内逐环节推进）三种形态驱动。**①与②不需要核心改动**（协作方皆接口、`Pipeline` 为纯数据）；**③需 `Step`/`Resume` 接口，不进一期**。**硬要求：任何形态都必须调用同一份 `Pipeline.Validate()`**——否则该形态会变成绕过不变量的后门。设计见 `xhunter-architecture.md` §5 |
| FR-1.10 | **驱动者无关性 + Bounty 自举**：任何能"准备 Bounty 文件 + 启动进程 + 消费 stdout 事件流"的实体都是合法驱动者（平台 daemon 只是其中之一；**本地运行的 UI/脚本同样合法，无需核心改动**）。为此补齐**Bounty 生成能力**：给定本地仓库路径 + 任务描述，探测 `remote` / 基线 commit（取 HEAD）/ 任务分支名 / 门禁候选（`.xhunter/gates.yml` 存在性）/ 预算与策略默认值，生成 Bounty 文件。**边界**：① 生成器**必须 clone 到临时工作区**，不得把用户当前仓库目录当工作区（§3 硬约束，且会污染用户的未提交改动）；② 生成过程**不得放松任何不变量**——门禁来源、凭据要求（需写权限）、模型无 git 能力一律不变；③ 生成器只是**便利工具**，不进入交付路径（平台仍可自行生成 Bounty） |
| FR-1.11 | **运行段看护（4 条）**：① **流看门狗**——L4 接收段不活动超时（`StreamIdleTimeout`，默认 120s）即 Cancel 并以环境错误收敛，流内挂起时长必须有上界；② **提交连败提前收敛**——检查点连续失败达上限（3 次）后，**本轮结束即进入终态收敛**，不跑完剩余轮次；③ **取消衔接**——L4 中途取消时已入队未执行的工具调用不执行，TurnRecord 按已执行部分配对落盘并标注 `cancelled`；④ **工具面定格**——模型可见工具面（原语集合 + 各自 schema + 符号路径可用性）在 L1 的 `ext.caps` **之后一次性定格**并存为任务状态；L2 工具说明层与 L3 请求都读这份定稿（单一事实源），不各自推导。其中**原语名字集合**由交付分期决定（环境能力不增减名字，FR-4.11），**符号路径可用性**由扩展能力决定——两者合并后才构成工具面 |

> **为什么"可组装"不以牺牲不变量为代价**：不变量从"代码里的固定顺序"升级为"**配置的合法性规则**"——例如"基线准备必须是 pre 的第一个环节"（INV-11）、"工具执行是 steps 的唯一写盘入口且检查点在其后"（FR-1.3c）、"必须有取消与预算守卫"（INV-3、FR-9.2）、"交付提交必须存在"（§3）。规则见 `xhunter-architecture.md` §4。

### FR-2 上下文获取（读）

| 编号 | 需求 |
|---|---|
| FR-2.1 | 支持按路径与行范围读取文件，超长内容截断时必须显式标注截断位置与总行数（**全文读取同样适用**：不带行范围的读取返回全文；超过单次护栏时在行边界收刀，显式标注已显示范围与**续读起点行号**（模型照抄即可，不必自己算加法）——不得静默截断） |
| FR-2.2 | 支持文件名模式匹配与内容检索，使用内置实现而非调用 shell 命令 |
| FR-2.3 | 支持列出文件内符号（名称、类型、签名、行范围） |
| FR-2.4 | 支持按限定名读取单个符号源码，用于在完整文件中只取目标片段 |
| FR-2.5 | 支持按名称跨文件检索符号定义 |
| FR-2.6 | **项目约定文件（AGENTS.md）**：发现与注入由**提示词插件**负责（FR-7.8）——内核不规定它在哪、叫什么、怎么解析；内核只保证两条固有性质：**构造一次即冻结**（运行中不因模型改动而重读，防缓存失效与自指循环）、**书写与生效分离**。默认插件按开放规范（[agents.md](https://agents.md)）处理，细则：文件名精确匹配 `AGENTS.md`；**嵌套最近优先**——模型操作命中某文件时，取该文件目录向上到工作区根的路径链上**最近且尚未注入**的 AGENTS.md 追加附注；根级 AGENTS.md 全文注入（属压缩"永不丢"等级，AC-17）；模型运行中**可以**修改 AGENTS.md——它是普通工作区文件，改动进交付 diff 由人 review（AC-20），只是本次已注入内容不热重载；跨任务演化走合并工作流，不做运行时自我修订 |
| FR-2.7 | 生成前应能采集 2-3 个同类文件作为风格样例，用于对齐既有代码约定 |
| FR-2.8 | 支持查询符号的引用点，用于影响面分析（依赖 FR-4 阶段三） |

### FR-3 代码生成与落笔（写）

| 编号 | 需求 |
|---|---|
| FR-3.1 | 修改已有文件前必须先读取该文件；未读取的写入请求必须被拒绝。**文件在读取后被外部改动（内容指纹变化）时，写入必须被拒绝并要求重新读取**——防止基于过期内容落笔（对齐 FR-5.1 的读回校验） |
| FR-3.2 | 文件修改必须使用精确替换。**已有文件一律走 `edit`；`write` 仅限新建**——"整文件重写已有文件"不是能力，而是应当排除的路径（"长文件"不可机械判定，策略引擎无法执行，故按可判定的规则表述） |
| FR-3.3 | 支持新建文件，且新建时需遵循工作区既有目录结构与模板 |
| FR-3.4 | 单次任务的变更需保持跨文件一致（实现、类型定义、测试、文档同步） |
| FR-3.5 | 所有读写路径必须解析后校验落在工作区根目录内，防止路径穿越与符号链接逃逸 |
| FR-3.6 | 生成代码的缩进、引号、导入顺序、注释密度必须跟随目标文件既有风格 |

### FR-4 符号级编辑

以语法解析为基础，把编辑目标从"一段文本"升级为"一个符号"。

**交付形态**：本节能力**不在核心二进制内实现**，而是以 MCP 扩展接入（见 FR-13）。核心保持语言无关、零解析器依赖；解析器与语言语法属于扩展侧，其选型不影响核心。

| 编号 | 需求 |
|---|---|
| FR-4.1 | **阶段一（只读）**：支持符号枚举与按符号读取，不涉及任何写回 |
| FR-4.2 | **阶段二（整体替换）**：支持按符号限定名整体替换符号体 |
| FR-4.3 | **阶段三（精细手术）**：支持在符号内指定位置插入，以及跨文件重命名符号 |
| FR-4.4 | **不变量：区间替换**。写回必须只改写目标符号的字节区间，其余字节原样保留。**禁止重新打印整棵语法树**，否则注释、空行与格式会被整体洗掉，产生无法 review 的巨型 diff |
| FR-4.5 | 源码存在语法错误时（含 `ERROR` 节点）必须能检测并降级到文本替换模式，给出显式提示而非失败 |
| FR-4.6 | 写入代码需按目标位置的缩进层级重排，并探测目标文件的缩进风格（制表符/空格、宽度） |
| FR-4.7 | 符号级编辑必须是文本编辑的超集。对无语法定义的文件类型（配置文件、模板、`.env` 等）自动使用文本模式 |
| FR-4.8 | 编辑失败必须以结构化错误返回（目标不存在、歧义、解析失败），便于模型自愈 |
| FR-4.9 | **不限开发语言**：能力选择不得因语言未支持而拒绝仓库或文件。任何语言的仓库都必须可被受理与完成，最低以文本路径运行（对应语言中立原则） |
| FR-4.10 | **语言注册机制**：内部路径由语言注册表驱动——已注册语言可提供符号路径，未注册语言自动走文本路径；新增语言不得改动上层工具契约（FR-4.11、FR-13.2） |
| FR-4.11 | **统一操作原语**：模型侧不暴露符号专用工具名。符号能力通过统一原语（`read` / `edit` / `find` / `rename`，见 §6）的内部分发呈现；模型无从感知工具来源与内部路径。工具面 = **7 个文件原语 + 1 个控制原语**（`checkpoint`）：控制原语不参与文件原语的分发体系，只承载"请求检查点"这一语义意图（FR-1.3c）。**工具面恒定**：集合只由**交付分期**决定，**不随环境能力漂移**——扩展不可用、语言未注册、扩展不具备引用解析能力，都不改变工具名与参数 schema（注册规则见 §6） |
| FR-4.12 | **分发规则**：内部路径由**选择器语法 + 语言可用性**共同决定——"语言已注册且语法可解析"且"选择器为符号寻址"时走符号路径，否则走文本路径并记录降级原因。**内部路径不同不得放宽匹配语义**：定位失败照旧显式报错（对齐 FR-4.4、FR-3.2） |
| FR-4.13 | **路径可观测**：每次调用在工具结果与事件流中如实上报 `resolved_mode`（symbol / text）、**精度等级**（syntactic / semantic）与降级原因，供远程诊断与内部命中率统计（对齐 FR-11.2、FR-11.5）。**不得把语法级结果当作语义级呈现** |

### FR-5 自检（验）

| 编号 | 需求 |
|---|---|
| FR-5.1 | 写入后必须读回变更内容，确认无截断与语法残缺 |
| FR-5.2 | 支持运行**受限校验命令**（白名单机制，如类型检查、静态检查、项目声明的校验脚本）。准确表述是：**不提供任意命令执行，提供的是对受审命令集合的"具名调用"**——模型只给门禁名（枚举），命令来自受审配置，`argv` 固定（FR-5.2b）。**实现不需要 shell**：`argv` 数组直启（fork+exec），超时/截断/非交互一律走内置实现，不调用 `timeout`/`head` 等外部工具 |
| FR-5.2b | **质量门禁是 `check` 原语的具名条目，不是新工具**：清单字段为 `name` / `argv`（数组直启不经 shell，**`argv[0]` 为 `sh`/`bash`/`zsh`/`dash` 一律拒绝**）/ `timeout` / `required` / `expect`（通过判据）/ `dir`（工作子目录，monorepo 需要）/ `env`（**显式声明的环境变量**，见 FR-5.2i）。**有三个来源，按优先级**——① **Bounty 下发**（平台显式配置，可覆盖/禁用仓库声明）② **仓库声明**（`.xhunter/gates.yml`，**从基线 commit 读取**，见 FR-5.2g）③ 都没有则不设门禁（`required` 为空 → 无"未运行即失败"约束）。**`expect` 必须可表达"非退出码"判据**（如 `gofmt -l` 的"输出为空"），否则格式门禁永远"通过"。门禁名注入上下文供模型调用。结果（名称 / 通过与否 / 是否命中缓存）进事件流与结果文件——它是 MR 评审最需要的证据。设计见 `xhunter-architecture.md` §7.3 |
| FR-5.2c | **门禁驱动的检查点**：门禁**通过**即立刻产生一个检查点（最强的"自洽状态"信号，FR-1.3c）；门禁**未通过**则抑制后续自动检查点，直到下一次通过或收尾交付——**破损状态不被钉住** |
| FR-5.2d | **门禁执行失败与判定不通过必须区分**：命令不存在 / 无法创建进程 / 超时 = **环境错误（退出码 2）**，不是质量结论；退出码非 0 或输出越阈值 = 质量不达标（终态失败，若 `required`）。任一 `required` 门禁未通过**或从未运行** → 终态失败（退出码 1），但改动照常交付（FR-6.5） |
| FR-5.2e | **门禁结果缓存**：按待提交改动的内容指纹缓存，同一状态重复调用返回缓存（标注 `cached`）。避免重复执行耗时的测试命令，也避免重复门禁调用产生重复检查点 |
| FR-5.2f | **门禁的执行主体（分两层）**：<br>· **主路径 = 模型通过 `check` 工具调用**——模型判断"何时值得验证"（改完一批相关文件之后，而非每次编辑），门禁通过即触发检查点（FR-5.2c）<br>· **兜底 = 收尾前自动补跑 `required` 门禁至少一次**——因为"required 门禁未运行"本身即判交付失败（FR-5.2d），若模型从未调用，整段工作会白跑；收尾自动补跑把"必然失败"变成"可能通过"，且此时的工作区正是**最终交付物**，结论才有针对性<br>两层都受同一策略框架约束：命令来自 Bounty 白名单、argv 直启、非交互、超时（FR-8.6）。自动补跑遵守墙钟预算——预算已耗尽则不再补跑，按"未运行"判失败 |
| FR-5.2g | **仓库声明的门禁从基线 commit 读取，不从工作区读取**（`git show <base_commit>:.xhunter/gates.yml`）。**理由不是"值不值得信任人类写的配置"**——仓库声明的门禁与 CI 配置一样，是**人类在 MR 中 review 过的配置**，可以信任；真正要防的是**模型在任务中途削弱自己的门禁**：工作区可被模型 `edit`，而基线 commit 由任务分支钉住、不可改。因此读取基线 = 冻结配置语义。辅以策略层拒绝模型写该路径（纵深防御，FR-8.7） |
| FR-5.2h | **任务本身是改门禁时**：默认"从基线读取"意味着新清单**本次不生效，下次成为新基线后才生效**（与 CI 惯例一致）。需要新清单本次生效时，**只能由 Bounty 显式授予**（`gates_source: working_tree`），并受三条护栏约束——**元门禁**（schema 合法 + 每个 `argv` 可启动）、**强度不得降低**（同名 `required` 门禁的 `argv`/`expect` 不得改动，只允许新增）、**显式上报**（`gate_config_changed` 事件 + 结果文件标注清单来源）。**模型拿不到豁免**：`gates_source` 只存在于 Bounty（Harness 的输入），模型既看不到也改不了 |
| FR-5.2i | **门禁子进程的环境与凭据隔离**：① **Xhunter 自身凭据（git 推送用）绝不得传给门禁子进程**——否则任何测试脚本都能读到并外泄（FR-8.4 的延伸）；② 传给门禁的环境 = 最小集（`PATH`/`HOME`/`LANG`/`CI=1`/`NO_COLOR=1`/`GIT_TERMINAL_PROMPT=0`）+ **清单里显式声明的 `env`**；③ 若某门禁确实需要凭据（如集成测试的数据库连接串），由**平台在 `env` 中显式给出**，并计入 FR-8.4 的"不得进入上下文/事件/交付物"约束 |
| FR-5.3 | 校验命令的输出需截断至合理长度并结构化为事件上报，避免污染上下文 |
| FR-5.4 | 结束前需对新引入符号做一致性检查：是否已定义、导入是否齐全、调用签名是否匹配 |
| FR-5.5 | 产出 patch 前需自审 diff，检出误删、调试残留、无关格式变更 |

### FR-6 交付

| 编号 | 需求 |
|---|---|
| FR-6.1 | **主交付**：任务分支上的提交链（阶段性检查点，交付 = 分支 tip，见 §3）；**附带交付**：相对基线的统一 diff（`git apply` 兼容，`git diff <base>..<tip>`），**排除会话材料路径 `.xhunter/<session_id>/**`**（按任务隔离；门禁清单等其他路径不排除），附基线 commit 与分支 tip SHA |
| FR-6.2 | 产出变更说明：改了什么、为什么、影响哪些文件 |
| FR-6.3 | **产出自作主张的假设清单**。信息不足时采取的最保守默认必须逐条列出，这是无人类场景下替代"追问"的唯一机制，也是平台侧的审计入口 |
| FR-6.4 | 标注不确定项与未覆盖风险，供下游 review 聚焦 |
| FR-6.5 | 若校验未通过，改动仍应交付（提交照常推送）但状态必须为失败，不得静默降级为成功 |

### FR-7 首轮提示词与组装

首轮固定为 `system` 与 `user` 两条消息，与协议首轮消息一一对应：前者放稳定内容（利于前缀缓存），后者放本任务的动态内容。**两段正文都由插件贡献**（FR-7.8）。

| 编号 | 需求 |
|---|---|
| FR-7.1 | 两段职责不混：**system 段** = 内核条款 + 项目约定与技能清单；**user 段** = 环境事实 + 任务描述 |
| FR-7.2 | 必须包含**无人类条款**（由内核拼入 system 段末尾，插件删不掉也改不动）：禁止提问、禁止请求确认、禁止等待输入 |
| FR-7.3 | 必须包含**止损规则**（同上）：同类失败达到阈值后换策略，仍失败即失败退出；预算不足立即失败，不得绕过 |
| FR-7.4 | 完成标准必须是可验证的（目标行为实现 + 通过既有校验 + 产出可应用 patch），不接受"尽力而为" |
| FR-7.5 | 环境事实（工作目录、平台、shell、包管理器、基线 commit、dirty 状态）必须运行时注入，禁止在模板中写死；**由内核注入 user 段**——这些是内核知道而插件无从知道的事实，交给插件陈述就会在换机器、换平台之后继续断言旧事实 |
| FR-7.6 | 按缓存友好顺序组装：稳定内容进 system 段，动态内容进 user 段 |
| FR-7.7 | 能在工具 schema 中表达的信息不得在提示词中重复描述 |
| FR-7.8 | **组装过程是扩展点**：两段正文由**多个插件**贡献、按**装配顺序**拼接（同一插件可同时挂在两段上）。约定文件如何发现、技能清单从哪来、正文写什么，全部由插件决定，内核不规定位置与格式。内核保留四条职责：**两段的位置与顺序**（插件给正文，不给消息序列）、**取一次并冻结**、**内核条款在 system 段末尾追加**、**不得越界**（正文改变不了工具面、策略裁决、路径边界与凭据边界） |
| FR-7.9 | 插件附带义务：单条素材非法（如一份写坏的技能说明）**跳过而非整体失败**，并**经事件流上报**降级；构造失败（基线读不了、扩展不可用）→ 退出码 2。少了系统提示词与项目约定而继续跑，产出只会慢慢偏出仓库约定，且没有任何一步会报错 |

### FR-8 策略与安全边界

无人类审批通道，**策略引擎即权限边界本身**。

| 编号 | 需求 |
|---|---|
| FR-8.1 | 读操作默认可行，但受工作区路径限制（FR-3.5） |
| FR-8.2 | 写操作受路径约束；工作区外的任何写入一律拒绝 |
| FR-8.3 | 禁止破坏性操作：递归删除、强制推送、硬重置、修改持续集成配置。**推送只允许 fast-forward**（远端 tip 必须是本地父提交）：推送到其他分支、改写已推送历史、删除分支一律拒绝 |
| FR-8.4 | 凭据只从环境变量注入，**不得进入模型上下文、日志、事件流与 patch** |
| FR-8.5 | 策略拒绝必须以结构化事件上报（被拒操作、拒绝原因），不得静默跳过 |
| FR-8.6 | 涉及需要交互确认的外部命令（版本控制、包管理器等）必须设置非交互环境变量，并对子进程关闭标准输入 |
| FR-8.7 | **路径级策略粒度**：策略必须能按「工具原语 + 内部路径（文本 / 符号）」分别裁决与拦截（例如允许文本路径、拒绝符号路径，或反向），并可按影响面阈值拦截；拒绝行为须结构化上报（FR-8.5）。这是统一原语（FR-4.11）下重建"工具即权限边界"的机制 |

### FR-9 预算与止损

| 编号 | 需求 |
|---|---|
| FR-9.1 | 支持四重预算上限：模型 token、费用、推理轮数、墙钟时间 |
| FR-9.2 | 任一预算耗尽立即终止，状态为失败并上报耗尽维度 |
| FR-9.3 | 不允许任何形式的预算绕过或自动延期 |
| FR-9.4 | 连续同类工具失败达到阈值触发策略切换，超过上限即失败退出 |
| FR-9.5 | **上下文窗口上限必须预置配置**：按 provider + model 维度配置，运行时**不得估算**。来源优先级：① **本地目录快照**（安装时从 LiteLLM 目录拉取，`xhunter models update` 可手动刷新）；② Provider 配置文件显式覆盖（自建网关、新模型）；③ 两者皆无 → **启动期显式失败**（退出码 2，环境问题可重试），不得以隐式默认值继续。字段与配置形态见 `xhunter-usage.md` §4 |
| FR-9.6 | 压缩水位线与可用输入预算由该配置推导：**可用输入预算 = `limit.context` − 固定开销（系统指令与工具 schema）− `limit.output`**；水位线默认 预警 70% / 目标 50% / 硬上限 90%（以可用输入预算为基数）。参数可配置但必须有默认值 |

> **上限类字段不得估算，行为类字段可降级**：`MaxContextTokens` 属前者——估算偏高会在任务中途触发硬失败，估算偏低会静默损害所有同类任务；启动期一次性显式失败，把问题暴露在任务开始之前，且退出码 2 的语义（环境问题可重试）正好承接"修好配置后重派"。`UsageReporting` 则属后者（本地估算即可，误差自校正）。

### FR-10 状态输出与心跳

外部通道只有一条：**stdout 事件流**（FR-1.4）。因此本节的"输出"一律指写入该通道，不涉及网络上报。

| 编号 | 需求 |
|---|---|
| FR-10.1 | 运行期间按固定间隔输出**任务级**心跳事件，与 runtime 心跳完全解耦 |
| FR-10.2 | 终态必须显式输出成功/失败/取消事件，不允许仅依赖退出码 |
| FR-10.3 | 心跳需携带当前阶段与已用量，供平台侧判断"运行中"与"卡死" |
| FR-10.4 | **通道断裂即终止**：事件（含心跳）**写入失败时记录并终止**，不得静默丢弃进度、不得假装仍在工作。stdout 是唯一通道，写失败意味着消费者已不在（EPIPE）或无法接收（磁盘满），属**环境问题，退出码 2**——平台可修好后重派 |

### FR-11 可观测与远程诊断

| 编号 | 需求 |
|---|---|
| FR-11.1 | 每次模型调用与工具调用均产出结构化事件，含耗时与用量 |
| FR-11.2 | 错误必须结构化：错误类型、上下文、是否可重试 |
| FR-11.3 | 全流程携带统一追踪标识，可串联平台侧记录 |
| FR-11.4 | 人类可读日志与机器事件流分离输出（事件流走 stdout，日志走 stderr） |
| FR-11.5 | 因无人查看终端，所有失败信息必须自含足以远程定位的上下文 |
| FR-11.6 | **生效配置快照**：启动时产出一份"本次 Hunt 实际生效的规则"快照——门禁清单（含**来源**：Bounty / 仓库声明 / 豁免）与各自 `required`、策略配置、预算上限、检查点策略、扩展能力指纹、目标平台。**进 `hunt_start` 事件并写入结果文件**。它同时服务远程诊断（FR-11.5）与 MR 评审（"这次验收用的是什么规则"），且**只读快照、不可由模型影响** |

### FR-12 幂等、清理与会话恢复

| 编号 | 需求 |
|---|---|
| FR-12.1 | **会话恢复（resume）**：投递给出 `XHUNTER_SESSION_ID`（= 延续一个既有会话）时进入续跑——分支与记忆都以会话标识为准（`xhunter/<session_id>`、`.xhunter/<session_id>/`），因此接的是同一条分支、同一份历史——clone/fetch 仓库 → checkout **任务分支 tip（最后一个检查点）**，该状态即上次工作区 → **读回会话材料**（`.xhunter/`，随检查点提交、由 git 保证完整性）→ 回灌上下文后继续推理。**不重放写操作**：上一个检查点之后的改动由模型在续跑轮自然重做（代价有界：最多一轮） |
| FR-12.2 | 会话材料自含续跑所需信息：对话历史（含每次工具调用与结果摘要）、写操作序列、turn 序号、用量。**随检查点提交进任务分支**，格式自描述且带 `schema_version` |
| FR-12.2b | **材料按任务隔离**：路径为 `.xhunter/<session_id>/session.jsonl`——**每个任务一个独立文件**。因此同一仓库多任务并行时各写各的材料，不存在交叉覆盖。**同一 Bounty 不并行执行**（一任务一分支一进程）；若平台违规并行，两端都会因 fast-forward 推送失败而**显式报错**，而不是静默冲突（FR-8.3） |
| FR-12.3 | **会话材料不可被模型篡改**：① 模型无 git 操作能力（INV-11），无法改写已提交历史；② 策略层禁止模型写入 `.xhunter/**`（FR-8.7 路径级策略）；③ 该路径不参与交付 diff（FR-6.1，排除范围即 `MaterialDir`）。**提交时必须强制加入**（`add -f`）——若仓库自身的 `.gitignore` 恰好忽略 `.xhunter/`，静默跳过会导致材料未随分支提交、续跑失效 |
| FR-12.3b | session 增量随事件流周期性落盘，与关键状态落盘同源，应对无法捕获的强杀信号 |
| FR-12.4 | 退出时必须回收全部子进程、临时目录与文件锁 |
| FR-12.5 | 清理失败不得阻断退出流程，但必须记录 |
| FR-12.6 | **恢复失败**（会话材料损坏或版本不兼容、任务分支不可达、checkout 失败）时显式失败，退出码 2，由平台 fallback 到干净基线重跑；resume 是优化，重跑是兜底，两者不互斥 |

### FR-13 扩展接入（MCP）

符号级能力以 **MCP 扩展**形式提供，核心不含解析器与语言语法。

> 本节讲的是**能力扩展**（给工具加后端）。**内容扩展**（提示词正文、项目约定、技能清单由谁提供）是另一回事，见 FR-7.8——两者都叫扩展，但前者扩展工具的能力面，后者只贡献文本，改不了工具面与权限边界。

> 本节讲的是**能力扩展**（给工具加后端）。**内容扩展**（提示词正文、项目约定、技能清单由谁提供）是另一回事，见 FR-7.8——两者都叫扩展，但前者扩展工具的能力面，后者只贡献文本，改不了工具面与权限边界。

| 编号 | 需求 |
|---|---|
| FR-13.1 | 支持以 MCP 接入本地扩展进程（stdio 传输）；核心不因扩展存在与否改变可用性 |
| FR-13.2 | **扩展对模型不可见**：扩展不新增模型可见的工具名，其能力通过统一原语的内部分发呈现（FR-4.11、§6）；扩展结果与内置结果在结构、错误语义上完全一致 |
| FR-13.3 | **写入落盘集中在核心**：扩展不直接写工作区，只返回定位结果（目标文件 + 字节区间 + 新内容），由核心执行区间替换。单一写入原语（FR-4.4）不因扩展而分裂 |
| FR-13.4 | 扩展缺失、启动失败或超时：相关**符号路径**不可用——**工具不撤回**（仍注册，FR-4.11），支持文本路径的原语退回文本模式；无降级形态的原语（`rename`）返回结构化错误。模型收到**显式提示**，任务不失败（对齐 FR-4.9、FR-4.10、AC-11、AC-26） |
| FR-13.5 | 扩展进程生命周期：懒启动（首次调用符号工具时拉起）、随 Hunt 退出回收（FR-12.4）；扩展崩溃可隔离，不得使主循环静默挂起（INV-3）。**注册即副作用、卸载即撤销**：扩展注册的一切（工具 schema、符号定位能力、能力描述符）随其卸载**全部撤销**，不留悬挂状态（对齐 INV-3） |
| FR-13.6 | 扩展处于**不可信边界**：仅允许本地进程；不得接触凭据（FR-8.4）；路径校验与写盘仍由核心执行，扩展无法绕过 FR-3.5 / FR-8.2 |
| FR-13.7 | 会话材料须含**扩展能力指纹**（扩展标识 + 版本 + 覆盖语言清单 + 后端与精度等级），**用于诊断**：能力变化可能解释"续跑后的精度与上次不同"。**不再作为重放闸门**——检查点恢复不依赖重放，故指纹不一致只记录、不阻断 |
| FR-13.8 | **后端抽象**：扩展**内部**以"能力声明驱动的后端抽象层"实现符号能力，后端可替换（自包含语法解析后端 / LSP 语义后端 / …）。核心不感知后端种类，只消费**能力描述符**（能力集 + 精度等级），据此决定符号路径可用性与结果标注 |
| FR-13.9 | **外部后端不得成为必需依赖**：依赖外部进程的后端（如 LSP 需按语言安装语言服务器）为可选后端，缺失时降级到自包含后端并**上报精度变化**（对齐 NFR-1、FR-13.4） |
| FR-13.10 | **协议托管 MCP 不采用**：OpenAI Responses 的内置 `type:"mcp"` 工具与 Anthropic Messages 的 `mcp_servers` 连接器把 MCP 客户端搬到**供应商侧**——工具由上游代跑、结果直接进上下文。它绕过策略裁决（上游调用不经 Policy）、绕过唯一写盘入口（工具执行永远在 Harness 侧），且仅支持公网 HTTPS 服务端（无法接本地 stdio 扩展）、凭据须交给上游。本项目的 MCP 仅限本地 stdio 扩展（FR-13.1、FR-13.6）；线格式包不发送也不消费这些字段（上游加字段按容错处理，不致解析失败） |

### FR-14 上下文压缩

| 编号 | 需求 |
|---|---|
| FR-14.1 | **水位线触发**：窗口按预警（默认 70%）触发压缩、目标（默认 50%）为压后水位、硬上限（默认 90%）视为不可继续。**不允许"超限才压"**——届时已无余量执行压缩后的那一轮推理。压缩后需有冷却期，防止震荡 |
| FR-14.2 | **分层压缩**：L0 工具输出截断 → L1 丢弃可重建信息（推理过程）→ L2 工具输出整体替换为可寻址摘要 → L3 旧轮折叠为结构化工作日志 → L4 模型摘要（可选）。按序下压，够用即停 |
| FR-14.3 | **保丢优先级**：永不丢——Bounty 正文与验收标准、工作区约定、当前轮 messages、**写操作记录**；优先保留——最近 N 轮的完整调用/结果对；可替换——早期工具输出；可丢弃——推理过程、重复失败细节、已被覆盖的中间态 |
| FR-14.4 | **确定性优先**：默认压缩**零模型调用**。结构化工作日志由 session 记录**投影**生成（FR-12.2），内容与顺序均可复现 |
| FR-14.5 | **模型摘要为可选最后手段**（L4）：若启用，须计入 token 预算（FR-9.1），且摘要文本**生成一次即落盘**、恢复时读回——不得在**恢复路径**上重新生成（对齐 FR-12.1） |
| FR-14.6 | **交付物不依赖上下文**：patch、变更文件清单、假设清单与未覆盖风险一律由 Harness 从 session 记录生成，不得依赖模型对压缩后历史的回忆 |
| FR-14.7 | **可观测**：每次压缩产出结构化事件，携带命中层级与释放的 token 量，供平台侧判断任务效率是否退化（对齐 FR-11.1、FR-11.5） |
| FR-14.8 | **恢复回灌走同一管线**：resume 时的上下文回灌使用与正常运行时相同的压缩规则，不做特殊处理；历史低于阈值则全量回灌 |

### FR-15 Skill 渐进式加载

| 编号 | 需求 |
|---|---|
| FR-15.1 | **格式对齐开放标准**（[agentskills.io](https://agentskills.io) 规范）：skill = 一个目录 + `SKILL.md`（YAML frontmatter：`name`（必填，1-64 字符小写字母/数字/连字符，须与目录名一致）+ `description`（必填，≤1024 字符）），可含 `references/`、`scripts/`、`assets/` |
| FR-15.2 | **三层渐进披露**：**发现**——启动时由提示词插件（FR-7.8）扫描 frontmatter，向 system 段注入"可用 skill 清单"（name + description，~100 token/条）；**激活**——模型按需以 `read` 原语读 SKILL.md 全文（<5000 token）；**执行**——references/ 等素材同样经 `read` 按需读取。全程**零新原语**（7 原语不变），前端清单只是上下文组装的一次性注入 |
| FR-15.3 | **来源与冻结语义**：目录位置属**默认插件**的约定（工作区内 `.xhunter/skills/`（不进交付 diff，随会话材料排除；策略禁止模型写）。清单与内容**从基线 commit 读取**（内核保证构造一次即固定）——与门禁清单同一语义：冻结配置、防模型中途改；`dir` 档（任意目录工作空间）下退化为文件系统读取并在结果中标注来源。**激活面只认基线冻结版**：模型可将新 skill 写入 `.xhunter/skills.draft/` 起草面（普通工作区路径，进交付 diff 由人 review），但正在执行的 agent 不得改完规则立刻按新规则继续跑；跨任务 skill 演化 = "模型起草 → 交付 diff → 人合并 → 成为下次运行的新基线" |
| FR-15.4 | **不做执行面**：`scripts/` 一期**不可执行**（7 原语无 shell，skill 不得成为绕过通道）；frontmatter 的 `allowed-tools` 字段**忽略**——素材不得自我授权（INV-4：权限裁决只出自 Policy） |
| FR-15.5 | **解析容错**：只解析 frontmatter 的 name/description 平面标量（标准库实现，零 YAML 依赖）；格式非法的 skill 跳过并在事件流上报（可观测降级，对齐 FR-13.4 精神），不阻塞任务 |
| FR-15.6 | **预算护栏**：发现清单有总量上限（建议 ≤50 条 / 溢出截断并上报）；SKILL.md 读取走通用截断（FR-2.1）与 L0~L4 压缩（FR-14），无豁免 |

### FR-16 模型接入（协议适配器）

| 编号 | 需求 |
|---|---|
| FR-16.1 | **模型调用一律经 Provider 适配器**：编排逻辑（循环、工具、上下文、策略）不认识任何具体协议与供应商；适配器是唯一知道"怎么与某个端点说话"的地方 |
| FR-16.2 | **协议实现与装配分离**：协议实现只说协议——入口是普通构造函数，只接受已解析的连接事实（端点、模型、鉴权头值、上限），不含"自己叫什么名字"的装配知识，也不做注册；**哪个配置值对应哪种协议、针对已知厂商该怎么连线，由组装层决定**。接一家新厂商 = 组装层加一条针对性工厂，协议实现、Harness、配置格式都不动 |
| FR-16.3 | **一个协议一个包**：协议实现之间互不引用；共用件（流式分帧、中立调用词汇、协议侧错误形状、上限契约）下沉到共用包，因此改一家不牵动另一家。协议包不依赖配置模型，可脱离本项目的配置体系被独立复用 |
| FR-16.4 | **协议事实不外泄**：请求形状、流式分帧、增量拼装、错误分类与可重试性判定都在适配器内，上游线格式类型不导出；Harness 侧只出现协议中立的消息、工具声明与事件 |
| FR-16.5 | **接入失败发生在启动期**：模型上限缺失、端点缺失、凭据引用解析为空、组装层没有该协议对应的工厂 → 显式失败（退出码 2），不得留到运行中途——无人值守时中途失败意味着已消耗的轮次与预算全部作废 |
| FR-16.6 | **响应异常不得静默**：流中断显式上报并标注可重试性；形状不成立的调用（参数非法、工具名不认识、字段未知）带结构化错误回灌模型，既不替模型猜，也不悄悄丢弃 |
| FR-16.7 | **内置协议清单**（可扩展，不是封闭集合）：OpenAI 兼容对话补全、OpenAI Responses、Anthropic Messages。三者的共同点是"把上游协议形状关在各自包里、以中立事件对外"；差异点（消息形状、流式分帧、收尾事件、错误分类）由各自实现负责。SDK 取值、默认端点与凭据头的对应关系见 `xhunter-usage.md` §4 |

## 5. 非功能需求

| 编号 | 需求 |
|---|---|
| NFR-1 | **无外部运行时依赖**。核心二进制自包含，不要求目标环境预装语言运行时或语言服务器；符号扩展为**独立自包含工件**（本地进程），同样不引入运行时依赖 |
| NFR-2 | **冷启动可控**。单任务启动开销应显著小于任务本身的执行时间；扩展懒启动，未触及符号能力时不产生开销 |
| NFR-3 | **解析性能**（扩展侧）。单文件符号解析应在毫秒级；大文件编辑不触发全量重解析 |
| NFR-4 | **并发安全**（扩展侧）。语法解析器实例非线程安全，需按并发单元隔离；语法树只读可共享 |
| NFR-5 | **资源上限**。支持内存与临时磁盘占用上限，超限按预算耗尽处理 |
| NFR-6 | **跨平台**。支持主流操作系统，路径与换行差异需统一处理。**一期范围：仅 linux/amd64**；跨平台能力为后续阶段目标，一期须按可移植方式实现（不引入平台相关假设），但不在验收范围内 |
| NFR-7 | **体积控制**。核心不含语言语法；语法随符号扩展分发、按语言分包，不编入核心二进制 |
| NFR-8 | **可测试性**。核心能力需可在无模型参与的情况下独立测试（解析、替换、patch 生成、策略判定） |

## 6. 工具集规格

模型侧暴露 **7 个文件原语 + 1 个控制原语**（M3 起的稳定工具面；M1/M2 为 6 个文件原语 + 1 个控制原语，`rename` 随 M3 上线）；符号能力的差异体现在原语内部路径，不体现为工具名（FR-4.11）。下表前 7 个是文件原语，走统一分发体系；最后一个 `checkpoint` 是**控制原语**，不参与分发，只表达"请求检查点"的意图。

| 原语 | 阶段 | 内部路径 | 定位 |
|---|---|---|---|
| `read` | M1 | 内置 / 扩展 | 按路径与范围读文件（标注截断）；M2 起支持按符号读、以及文件的符号视图（枚举） |
| `write` | M1 | 内置 | **仅新建文件**（覆盖已有文件一律走 `edit`，FR-3.2） |
| `edit` | M1 | 内置 / 扩展 | 内容寻址的精确替换（改前必读 + 唯一性失败返回可诊断错误）；M2 起支持符号寻址：符号体替换、符号内插入 |
| `find` | M1 | 内置 / 扩展 | M1：内容检索（等价文本检索）；M2/M3：按名称定位符号定义、查询引用点 |
| `rename` | M3 | 扩展 | 跨文件符号重命名（一次调用完成全部改动）。**能力缺失时仍注册**，调用返回结构化错误（见下"注册规则"） |
| `glob` | M1 | 内置 | 文件名模式匹配 |
| `check` | M1 | 内置 | **具名质量门禁**（清单白名单，argv 直启不经 shell）：既是自检手段，也是**检查点的触发源**（门禁通过 → 检查点）。**不是任意命令执行**——模型只给门禁名（FR-5.2/5.2b/f） |
| `checkpoint` | M1 | ——（控制原语） | **请求一个检查点**：模型提议"此刻值得钉住"，并给出语义摘要（**上限 120 字，单行**）。**不暴露分支、远端、推送目标**；提交信息由 Harness 合成——摘要只作素材（只取首行、剥控制字符、超长截断），前缀与分隔符由引擎固定，因此模型无法借它伪造提交结构。密度策略仍是兜底——模型不调用照常按策略提交，模型调用只是"额外提前"；**无改动则不提交**，但意图照样被消费。约束：每轮最多 1 次（FR-1.3c） |

**参数形状（JSON Schema，已定格）**：与 MCP 的 `inputSchema`、两家 function calling 的参数格式同源——一份声明原样交给任意一方，适配器只翻译信封、不碰形状。逐字发往上游，故描述从简。

| 原语 | 参数（`*` = 必填） |
|---|---|
| `read` | `path*` 工作区内相对路径 · `range{from,to}` 按行区间（1 起、闭区间；省略读全文） · `symbol` 限定名（按符号读） · `in_symbol` 符号内相对定位 · `file_view` 改为列出符号大纲 |
| `write` | `path*` · `content*` 完整内容 |
| `edit` | `path*` · `content*` 替换成的新内容 · `literal` 内容寻址的字面量 · `symbol` + `in_symbol` 符号寻址 |
| `find` | `literal` 检索片段 **或** `symbol` 定位定义（二者至少其一） · `path` 限定文件 · `scope` 限定目录/包 |
| `rename` | `symbol*` 待重命名符号 · `new_name*` 新名称 · `path` 限定文件 |
| `glob` | `scope*` 文件名模式（如 `*.go`） |
| `check` | `name*` 清单里的门禁条目名 |
| `checkpoint` | `summary*` 为什么这里值得留检查点 |

两条纪律由测试守着：**schema 声明的每个属性名绑定层都必须收得下**（否则模型照说明书填的参数会被拒，而错在它看不到的地方）；**`additionalProperties: false`** 与绑定层"拒绝未知字段"是同一句话的两处表述。

**注册规则（FR-4.11）**：工具面由**两个互不相同的轴**决定，必须分开看。

| 轴 | 情形 | 行为 | 理由 |
|---|---|---|---|
| **交付分期**（决定是否注册） | 该能力在本次构建中**尚不存在**（如 M1/M2 无 `rename`） | **不注册** | 注册一个必然失败的工具只会浪费模型轮次 |
| **环境能力**（不决定注册） | 扩展不可用 / 语言未注册 / 扩展不具备引用解析能力 | **恒定注册**，调用时退回文本路径或返回**结构化错误** | ① 工具面不随环境漂移，prompt 前缀与 schema 稳定（缓存友好）；② 模型可据结构化错误自愈换策略（FR-4.8）；③ 环境能力是**运行时**事实，不应反馈到**工具契约**层 |

判据：**"这个能力在本次构建里存在吗"决定是否注册；"这个环境此刻支持吗"不决定注册。**

**实现可替换（原语扩展点）**：注册的是**名字**，名字背后的**实现**可由装配层替换（`NewRuntime` 差量替换 / `NewRuntimeWith` 整体接管）。边界与注册规则同源：overrides 只能替换**已知名字**的实现、不能新增工具名——发明新名字等于让模型可见面漂移，装配期即拒绝（退出码 2）。替换实现不改变模型可见的声明（名字与描述不变），因此也不影响前缀缓存。

**`rename` 的注册**：它是唯一"没有有意义降级形态"的原语——无法解析引用时，单文件文本替换是 `edit` 而非 `rename`。因此能力缺失**不导致不注册**，而是调用时返回结构化错误（如"当前环境不支持跨文件重命名，请改用 `edit`"），**不静默降级为文本路径**——那只会产出一个改了声明、没改调用点的半完成重命名。

**分发规则（FR-4.12）**：

```
可用符号路径 = 目标文件语言已注册（扩展可用） 且 语法可解析（无 ERROR 节点）
走符号路径   = 选择器为符号寻址（限定名 / 符号内位置） 且 可用符号路径
否则         → 文本路径（记录降级原因并随结果上报）
```

**四条硬约束**：

1. 路径由**选择器语法 + 语言可用性**共同决定——模型用表达方式选择路径，而非猜测工具名；
2. 内部路径不同**不得放宽匹配语义**：文本路径的唯一性校验、符号路径的定位失败，都必须显式报错；
3. 每次调用上报 `resolved_mode: symbol | text` 与降级原因（FR-4.13）；
4. **分发先于裁决**（顺序约束）：分发是纯函数（无副作用），在策略裁决之前完成，策略因此能按「原语 + 路径 + 影响面」拦截（FR-8.7）；符号路径的引用解析等**只读定位**同样在裁决前进行，使影响面对策略可见。

**能力 → 原语映射**：

| 原能力 | 现归属 |
|---|---|
| 内容检索 | `find`（文本路径） |
| 符号枚举 / 按符号读取 | `read`（符号路径） |
| 按名称跨文件定位定义 / 引用点查询 | `find`（符号路径） |
| 符号体替换 / 符号内插入 | `edit`（符号路径） |
| 跨文件重命名 | `rename`（独立原语） |

**明确不提供**：通用命令执行工具、网络访问、包管理器操作，以及**任何 git 操作**——分支创建、提交与推送属初始化与收尾阶段的固定职责（INV-11），**不作为工具暴露给模型**；因此也不存在"模型推到错误分支"的可能（FR-8.3 的策略规则是第二道防线，第一道是**没有这个能力**）。

## 7. 验收标准

| 编号 | 验收项 |
|---|---|
| AC-1 | 给定一个任务与干净基线，能产出可成功应用的 patch，且 patch 中不含与任务无关的格式变更 |
| AC-2 | 对包含语法错误的文件执行编辑，不崩溃、不静默失败，走降级路径并显式提示 |
| AC-3 | 对含重复模板代码的文件执行定点修改，能精确命中目标位置，且证明不会误改其他位置 |
| AC-4 | 任务信息不足时，进程不挂起等待，而是继续执行并在结果中列出假设 |
| AC-5 | 预算耗尽时立即终止并上报耗尽维度，无绕过行为 |
| AC-6 | 运行中发送 SIGTERM，进程在约定时间内退出，子进程与临时文件已清理，终态为取消 |
| AC-7 | 崩溃后重派：**平台向新机器投递同一会话**（`XHUNTER_SESSION_ID` 不变），能 checkout 任务分支 tip（最后检查点）、读回会话材料并继续推理；产出与上次检查点一致的工作区，且**未重做已完成轮次**；恢复失败时以退出码 2 显式失败 |
| AC-8 | 凭据不出现在事件流、日志、patch 与 session 记录中（需有自动化断言） |
| AC-9 | stdout 全部为合法事件行，无杂质 |
| AC-10 | 全程无任何等待标准输入的路径（静态扫描 + 运行断言） |
| AC-11 | 对**未注册语言**的仓库执行任务：能正常受理并完成，走文本模式，且在事件流与结果文件中显式标注精度降级；不出现"语言不支持"导致的拒绝或失败 |
| AC-12 | **扩展缺失/启动失败**时：任务仍能受理并完成（文本路径），事件流与结果文件如实上报扩展不可用与降级原因；核心能力不受影响 |
| AC-13 | **分发正确性**：同一原语在不同文件上落到预期路径——未注册语言 / 语法错误 / 无语法定义文件 → 文本路径；已注册且语法可解析 + 符号寻址选择器 → 符号路径。`resolved_mode` 如实上报；且内部路径不同**不放宽匹配语义**（两条路径的定位失败均显式报错） |
| AC-14 | **后端可替换**：替换符号扩展的内部后端（如自包含后端 ↔ LSP 后端）不改变工具名、参数与结果结构；精度等级随结果如实上报；外部后端缺失时自动降级且任务不受阻 |
| AC-15 | **读取后校验**：文件在读取后被外部改动（内容指纹变化），写入被拒绝并返回可诊断错误；重新读取后可正常写入。需有自动化断言 |
| AC-16 | **路径级策略**：策略可仅拦截符号路径（如拒绝跨文件重命名）而放行文本路径；拒绝行为结构化上报，且被拒操作不产生任何落盘 |
| AC-17 | **压缩保真**：触发压缩后，"永不丢"内容（Bounty 正文与验收标准、工作区约定、写操作记录）仍存在于上下文中；结果文件（patch、变更文件清单、假设清单）不因压缩缺失任何已发生的改动 |
| AC-18 | **压缩可观测且可复现**：每次压缩产出 `context_compacted` 事件（携带层级与释放 token 量）；同一 session 记录两次投影生成的工作日志内容一致（零模型调用） |
| AC-19 | **通道断裂**：stdout 写失败（模拟下游关闭管道）时，进程记录原因并以退出码 2 终止，不静默继续（FR-10.4） |
| AC-20 | **交付形态**：任务分支上形成提交链（密度由 `checkpoint.mode` 决定，默认 `on_structure`），分支在启动阶段即可见于远端；**交付 = 分支 tip**；只允许 fast-forward 推送，冲突时拒绝并退出码 2，**绝不 force push**；附带 diff **排除会话材料目录** `.xhunter/<session_id>/`（不排除该目录以外的 `.xhunter/` 路径，如 `skills.draft/**`，见 AC-25） |
| AC-21 | **推送边界**：策略拒绝推送到非任务分支、拒绝改写已推送历史与删除分支（FR-8.3） |
| AC-22 | **检查点自愈与止损**：单次提交失败不中止任务（下一轮累积重提）；连续失败达上限 → 环境错误。**密度可配**：给定 `mode=interval/interval=3` 时，三轮写操作只产生一次提交；`final_only` 只在收尾提交 |
| AC-23 | **AGENTS.md 规范**：根级 AGENTS.md 存在时全文注入 system 段且压缩后仍在（对齐 AC-17）；monorepo 嵌套场景下，模型读/写/编辑命中某文件后，其结果附注携带路径链上最近且未注入过的 AGENTS.md；文件名大小写不匹配（如 `agents.md`）不作为规范文件注入；运行中模型改动 AGENTS.md 不影响本次运行的注入内容（书写/生效分离） |
| AC-24 | **Skill 渐进加载**：启动时事件流含 skill 清单（仅 name+description）；模型未请求时 SKILL.md 全文**不出现**在上下文；`read` SKILL.md 走正常策略裁决与截断；模型写入 `.xhunter/skills/**` 被策略拒绝；非法 frontmatter 的 skill 被跳过且事件流可见；`scripts/` 无任何执行路径 |
| AC-25 | **书写/生效分离**：模型写入 `.xhunter/skills.draft/**` 被允许且进交付 diff；但该内容不出现在本次运行的发现清单中（激活面只认基线冻结版）；模型运行中修改 AGENTS.md 后，上下文中的项目约定与附注保持构造时内容不变 |
| AC-26 | **工具面恒定**：扩展**不具备引用解析能力**时，`rename` **仍然注册**（工具名与参数 schema 不变），调用返回结构化错误且**不降级为文本路径**；扩展不可用或语言未注册时，工具名集合同样不变（仅符号路径退化为文本路径）。**对照**：M1/M2 少 `rename` 属"分期未交付"这一独立轴，不构成工具面漂移（FR-4.11、§6 注册规则） |
| AC-27 | **协议与装配分离**：新增一家厂商只需在组装层加一条针对性工厂——协议实现、Harness、配置格式都不动；厂商特有差异（鉴权头的名称与前缀、端点约定）只影响组装层；组装层没有对应工厂时**启动期**以退出码 2 失败并指出该动哪里；协议实现里不出现配置里的 SDK 值、不做注册、不依赖配置模型；Harness 侧不出现任何上游线格式类型（FR-16） |
| AC-28 | **响应异常不静默**：流在上游报错或未给结束标记时中断 → 显式 `error` 事件（带可重试性）；参数非法 / 工具名不认识 / 字段未知的调用 → 带结构化错误的失败结果回灌模型，`tool_result` 事件如实上报；两者都不得被当成"正常结束"或"调用成功"（FR-16.6） |
| AC-29 | **组装可扩展**：首轮 system / user 两段正文由插件贡献——同阶段多插件按装配顺序拼接（换顺序即换结果）、空正文的插件不留下空行、每段各只调用一次；内核条款（工具纪律、安全边界、无人类条款、止损规则）始终拼在 system 段末尾且插件无法删改；插件构造失败 → 退出码 2 且原因指明是哪一段；两段都不接插件时只记 warn、任务照常（FR-7.8、FR-7.9） |

**验收环境**：一期全部验收项（含 AC-6 的信号行为）在 **linux/amd64** 上执行；跨平台验收（Windows 信号等价物等）随 NFR-6 推迟到后续阶段。

## 8. 分期计划

| 阶段 | 内容 | 价值 |
|---|---|---|
| **M1 最小可用** | 进程契约、git 基线获取与**任务分支 + 阶段性检查点 + 交付推送**、**6 个原语**（`read`/`write`/`edit`/`find`/`glob` 仅文本路径 + **`check` 具名门禁**；`rename` 在 M3）、内置提示词、整体 diff 交付、策略与预算、事件流、**会话材料随检查点提交**。**目标平台：linux/amd64** | 可接入平台跑通端到端 |
| **M1.5 会话恢复** | resume：checkout 任务分支 tip（最后检查点）+ 读回会话材料 + 回灌上下文继续（**不重放写操作**）；恢复失败 fallback 重跑 | 跨机器 failover，长任务崩溃不全损 |
| **M2 读精度与符号替换** | **MCP 扩展接入框架 + 分发引擎**（FR-4.11~4.13）+ 首个符号扩展：`read`/`edit`/`find` 获得符号路径（符号视图、按符号读取、符号体替换），首发语言 = Go。**工具名不变** | 解决"读不准、改错位置"的核心痛点 |
| **M3 手术能力与校验** | 符号内插入（`edit` 符号路径）、**`rename` 原语上线**（含引用解析）、影响面分析；按优先级扩充扩展的语言覆盖 | 从"能改"到"改得对" |

M1 不包含符号路径，是刻意的——先把协议跑通，再提升单点质量。**`check` 在 M1 但限定为具名门禁**（受审清单 + argv 直启），不是任意命令执行；它同时承担检查点触发源的角色。M1 的会话材料**随检查点提交**，恢复能力本身在 M1.5 补齐。**M2 起工具名不再变化**：能力增强体现为同一原语内部的路径升级，模型侧提示词与工具 schema 保持稳定。
