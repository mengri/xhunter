# Xhunter 产品设计

## 0. 文档定位

- 本文定义 Xhunter 的**产品边界与功能需求**：解决什么问题、明确不做什么、具备哪些能力、如何验收、如何分期。
- 实现结构（分层、组件规格、控制流时序、接口验收）见 `xhunter-architecture.md`；使用与集成方式（CLI、Bounty、事件流、结果文件、退出码）见 `xhunter-usage.md`。
- 基线假设：Xhunter 作为**平台侧 executor** 被调度运行，**不存在任何面向人类的交互界面**（无 TUI、无 Web UI、无审批弹窗、无多轮追问）。
- 平台范围：**一期仅支持 linux/amd64（单目标）**。跨平台（NFR-6）保留为架构约束，但不在一期验收范围内；一期实现**不得引入平台相关假设**（路径分隔符、大小写敏感、换行、信号语义等一律按可移植方式处理），以保证后续兑现跨平台时不需要返工。
- 编号规则：`FR-x` 功能需求，`NFR-x` 非功能需求，`AC-x` 验收标准。编号用于跨文档引用，不建议重排。**带字母的子编号（如 `FR-12.2b` / `FR-12.2c`）必须有自己的定义行**——不得只在别的条目正文里被命名：被引用却在正文里命名，引用处就指不到一条独立的需求，交叉引用体检会把它报成悬空引用。
- 验收环境：一期在 **linux/amd64** 上执行（见 §7）。

### 0.1 命名与术语

命名体系取自 Tavern 的酒馆 + 猎手世界观：**告示板上挂着悬赏令，猎手接单出门，办完回来交差。**

| 术语 | 含义 | 使用范围 |
|---|---|---|
| **Tavern** | 平台 | 已有 |
| **Xhunter** | 本系统的执行体（即本文档描述的对象） | 产品名与文档写作 `Xhunter`；二进制与包名写作 `xhunter` |
| **Harness** | Xhunter 内部的控制循环层 | 架构层名 |
| **Bounty** | 一次任务的委托（任务描述、工作区、预算、策略） | 取代原"任务文件"的说法 |
| **a Hunt** | 一次执行（一个进程的生命周期） | 取代原"运行"的说法 |
| **Session** | 同一会话的执行记录（写操作序列与上下文），可跨机器**续跑**（检查点恢复） | 会话可与多次投递（bounty）关联：同一 `session_id` 下的多次投递**共享记忆与分支**；不传时本次自成新会话 |
| **提示词插件** | 构造首轮 system / user 两段正文的扩展点：**多个插件按装配顺序拼接**（FR-7.8） | 正文由插件给；内核只保留两段的位置与顺序、取一次冻结、内核条款不可覆盖 |

**命名规范（强制）**：产品名 `Xhunter`（X 大写、h 小写，不写作 `XHunter`）；二进制名、包名、环境变量一律全小写，环境变量前缀 `XHUNTER_*`。跨平台大小写敏感度不同（Linux 敏感、Windows 不敏感），必须一次性定死。

**X 的语义**：读作 **cross（跨）** —— 对应"跨机器、跨 runtime 的 failover"，与「智能体不绑机器」的核心设计一致。

**三层隐喻**（仅用于文档与沟通，不进代码）：

| 隐喻 | 对应 |
|---|---|
| 马（有力量、无方向） | 模型 / LLM |
| 挽具与缰绳（把力量导向目标） | Harness —— 工具调度、上下文组装、循环控制 |
| 骑手（决定去哪、做什么） | Xhunter —— 任务执行策略 |

推论：**换马不换挽具** —— 更换模型或供应商不需要改动 Harness。

## 1. 目标与背景

### 1.1 要解决的问题

在无人值守的场景下，把"一个自然语言任务描述"稳定地转化为**交付物**——通常是一份可应用的代码变更，**也可以是任务本身要求的产出一份结论 / 小结**（此时那份最终答复就是交付物）——并让平台侧能够远程判断它处于什么状态（完成 / 待补条件 / 失败）。**合入与发布不在本系统的决策范围内**。

### 1.2 设计原则

| 原则 | 含义 |
|---|---|
| **无人类原则** | 任何"等待人类输入"的路径都是缺陷，不是降级策略。所有决策必须由策略引擎预先裁定 |
| **显式失败原则** | 宁可明确失败，也不允许静默成功。所有失败必须显式、可分类、可远程诊断 |
| **判据优先于偏好** | 终局是无人开发、乃至无人 review，因此判据必须是**可执行的证据**（门禁结果、读回校验、diff 可应用），而不是"改动面偏大""可能白做"这类规模与风险偏好。推论：**凡"因为怕白做而先拦住"的限制一律不设**（如影响面阈值）；正确性、权限边界与成本上限三类约束照旧。质量由**后验证据**判定，不由策略**先验预判**；**"任务白跑"不作为判据**——判据是"这次交付有没有证据"。**由此推出 V（评估接口）的补法是判据路线**：具名门禁（架构 §7.8）＋ 结构检查，两者都是可执行的证据（同一份改动两次跑同一门禁，结论相同）。**不采纳"派一个 agent 去评审"**（对抗性验证）：它的输出是另一个模型的**判断**，既不"可执行"也不"可复现"，与本节定调相反（备查见 `xhunter-memo-multi-agent-route.md`） |
| **只碰必要字节原则** | 变更范围必须收敛到最小，不产生无关噪音。这是 patch 可 review 的前提 |
| **语言中立原则** | 任务的受理与执行**不以开发语言为条件**。核心保持语言无关，符号级能力以**扩展**形式外挂；扩展缺失或语言未注册时自动降级为文本模式，任务照常执行而非被拒绝 |

### 1.3 非目标（明确不做）

| 不做 | 原因 |
|---|---|
| 交互式界面 / TUI / 进度可视化 | 无人类消费者 |
| 多轮澄清提问、审批弹窗 | 无人类可问，且会成为死锁源 |
| 任意命令执行（通用 bash 工具） | 权限面过大，与本设计的安全边界冲突 |
| 测试运行与长时间构建（除门禁外） | 越出"生成代码"的职责边界 |
| 部署、发布、合并决策 | 交付止于**任务分支上的提交**（FR-6.1）；合并与发布归平台侧 |
| 任务分支之外的版本控制写操作 | 不改历史、不 force push、不删分支、不操作其他分支（FR-8.3） |
| 多模态输入输出 | 与编码任务无关 |
| 交互式恢复 UI / 跨 Bounty 会话语义 | 确定性 resume（**检查点恢复**，不重放写操作）属 In Scope（FR-12.1），但无界面、无人工介入；恢复只发生在同一 Bounty 的重派 |

## 3. 运行模型

- **一个进程 = 一个 Bounty = 一次 Hunt**。进程启动即开始，进程退出即终结，不提供进程内复用与跨任务会话。
- **一个任务一个独立分支，分支由 Xhunter 创建并推送**：启动阶段（**任何模型推理与任何写操作之前**）在基线 commit 上创建任务分支并推送，把基线**钉在远端**；交付阶段把改动作为提交推送到同一分支。**这两件事都由 Harness 在固定阶段执行，不由模型驱动**——工具面不含任何 git 操作，模型既看不见也改不了分支名、推送目标与提交内容（INV-11）。分支一旦建立，resume / failover / 交付全部走分支，不再有"基线可获取性"问题。**推送目标只能是 Bounty 指定的任务分支**（FR-8.3）。
- **Xhunter 只针对 git 仓库操作，不依赖 local 工作目录**。投递必须给出仓库信息（远端 + 基线 commit + **任务分支名**）；**是否延续既有会话由"是否给出 `XHUNTER_SESSION_ID`"决定**（见 FR-12.1）。
- **投递而非拉取（Xhunter 侧）**：**Xhunter 不主动联系平台**。一次投递由平台交给进程（命令行给任务正文，环境变量给仓库与模型接入，FR-1.1）；**pull 留在平台侧**——由平台的调度器（如 Tavern daemon）拉取任务、再投递给具体机器。若平台希望"主动领取"语义，应由平台侧 sidecar 实现，Xhunter 保持不变。
- **任务活跃度挂在 Bounty 上，不挂在 runtime 上**。心跳必须按 Bounty **输出**（外部事件通道 = stdout，见 FR-1.4），与 runtime 心跳解耦——否则承载它的机器崩溃时，该任务会永久停留在运行中状态。
- **交付物是任务分支上的提交链**，不是"改动后的工作树"这个中间态。规则（保证线性、可复盘）：
  1. **阶段性提交**：按**任务配置的检查点策略**（FR-1.3c）提交并推送，分支 tip 随任务推进而前进；**交付 = 分支 tip**。提交内容 = **本轮已应用的改动**（工具已在同一轮的响应处理段执行完毕）。两条不变量与策略无关：**无新写操作不提交**、**收尾必提交**；
  2. **只允许 fast-forward 推送**：远端 tip 必须是本地父提交，**绝不 force push、绝不改写已推送历史**（FR-8.3）；
  3. 同时产出**相对基线的整体 diff** 作为附带产物，供 review 与平台展示（FR-6.1）；该 diff **排除会话材料路径**（`.xhunter/**`）。
- **恢复靠检查点而非重放**：崩溃后重派时 checkout 分支 tip（最后一个检查点）即为工作区状态，再读回会话材料继续推理。**不再重放写操作**——检查点之间的改动由模型在下一轮自然重做（代价是有界的：最多一轮）。
- **澄清回路：无人值守 ≠ 无人干预**。运行中若发现**任务描述与项目约定都没有给出**的必要事实，不走"追问"（运行期没有可问的对象），而是把**需要补全的清单**随终态上报（`status=blocked` / `reason=needs_input` / 结果文件 `needs`；**退出码取 0**——它不是失败：进程正常结束、清单已产出、改动已交付；**分类完全由 `status` 承载**——它是给平台与人的依据，**合入与否由平台与人决定，不在 Xhunter 契约内**）。**「继续做完」还是「立即停下」由模型判断**——依据是任务描述与项目约定（不同用户、不同任务的严谨度要求不同，任务描述里写明了就按它办），**引擎不规定固定策略**，只负责执行模型的判断：读到「## 需要补全」小节即收敛。**改动照常交付**——检查点已提交、分支 tip 保留，人补齐条件后从 tip 续跑（这正是"不重做已完成轮次"的前提）；人据此补齐条件，生成**新 Bounty** 并带**同一 session** 重投 → 走 resume：checkout 分支 tip ＋ 读回材料，从**下一轮**继续，**不重做已完成轮次**。干预因此发生在**投递层**（异步、有边界），而不是运行期（同步、会挂死）。平台对 `blocked` **不要合入**（也无需重派）——缺的是条件，等人补齐后带同一 session 重投。
- **同一 Bounty 不并行执行**：一任务一分支一进程。材料按 `.xhunter/<session_id>/` 隔离，故**多任务并行同一仓库互不干扰**；若平台违规并行同一 Bounty，两端的 fast-forward 推送会**显式失败**（环境错误），不会静默产生分叉或覆盖。

## 4. 功能需求

### FR-1 任务生命周期与进程契约

| 编号 | 需求 |
|---|---|
| FR-1.1 | **投递形态：任务内容与部署事实分离**。命令行参数给出**任务正文文件路径**（只含任务描述，含验收标准）；**仓库事实（远端地址 + 任务分支 + 基线 commit）与模型接入由环境变量给出**（`XHUNTER_*`），因此同一台机器上跑多个任务不必重复声明部署信息。字段清单与缺省值见 `xhunter-usage.md` §3 |
| FR-1.2 | 启动后从环境变量读取凭据，不读取本地凭据文件。凭据需具备**推送任务分支的写权限**（只读凭据无法完成交付） |
| FR-1.3 | 启动时获取基线：clone/fetch 仓库 → 校验基线 commit（`XHUNTER_REPO_BASE_COMMIT`）可达（按 SHA 浅克隆；不可得时退化为完整克隆）→ **在基线 commit 上创建任务分支并推送**（把基线钉在远端；分支已存在且 tip 为基线或其后代 → 视为续跑，幂等成功；否则环境错误）→ checkout。**本步骤属初始化，先于任何模型推理与任何写操作**；工作区必须干净 |
| FR-1.3b | **阶段性提交（检查点）**：提交累积自上一个检查点以来的全部改动，因此单次失败可在下一轮自愈；**连续失败达上限（默认 3 次）即环境错误**——远端不可用是环境问题，应当在**有界时间内暴露**，而不是跑完全程再报同一个错。**只允许 fast-forward 推送**（FR-8.3）。密度由 FR-1.3c 决定 |
| FR-1.3c | **检查点触发优先级 + 时间语义**：工具执行统一在**流结束后**（运行段 L5 响应处理），每轮**单一提交点在轮收敛（L6）**，**提交内容 = 本轮已应用的改动**（工具已执行完毕）。触发优先级：<br>① **门禁通过**（本轮 `check` 通过 → 轮收敛必提交，FR-5.2c）<br>② 模型显式 `checkpoint`（语义声明）<br>③ **结构检查通过**（语法级自洽，FR-1.3d）<br>**三者皆不满足 → 不提交**。**自动检查点只落在结构完整点上**——刻意没有「按轮提交」这一档：语法残缺的中间态钉在分支上价值很低（残次品不是可用的检查点，还会污染提交链）；判据不可判定（扩展未接入 / 语言未注册）时同样**不提交**。两条不变量：**无新写操作不提交**、**收尾必提交**（收尾的交付提交照常，改动不会因不产生自动检查点而丢失）。完整时序见 `xhunter-architecture.md` §6 |
| FR-1.3d | **结构检查（自动判定，不依赖模型自报）**：判据为 ① 目标文件**语法完整**（`ParseOK`）；② 单次编辑的字节区间**封闭在某个符号范围内**（需扩展提供符号范围，M2 起可用）。`ParseOK` 由 false 转 true 表示刚补全了一段代码；区间封闭表示"完整写完/替换了一个方法"。**判据是必要不充分的**：只识别"结构完整点"，不识别"功能完成"，语义完成仍由模型判断（FR-1.3c 的模型 `checkpoint`）。<br>**三态判定，"不可判定"与"未完成"必须分开**：<br>· **通过** → 提交（检查点落在"写完一个方法"这类结构边界上）<br>· **可用但未通过**（存在语法残缺）→ **不提交**，等下一个结构完整点<br>· **不可判定**（语言未注册 / 扩展未接入）→ **不提交**：宁可不留检查点，也不留残次品。代价是这类仓库只在收尾提交一次——这是刻意的取舍（把语法残缺的中间态钉在分支上既不可当检查点用、又会污染提交链），而收尾的**交付提交照常**，改动不会丢 |
| FR-1.4 | 全流程 stdout 输出结构化事件流，stdout 不允许出现非事件内容 |
| FR-1.5 | 结束时写出结果文件（状态、patch 路径、用量、错误、假设清单、**session 增量**）。`session_delta` 取**最小事实集**：`{turns_from, turns_to, ops_count}`——回答"这次接上了哪几轮、写了多少次"，而不是把整份材料复制进结果文件 |
| FR-1.6 | 通过退出码表达可分类的终态（见 `xhunter-usage.md` §7） |
| FR-1.7 | 收到 SIGTERM 后停止发起新的模型调用与工具调用，落盘当前状态与已有变更（含 session 增量），然后以被取消状态退出 |
| FR-1.8 | **流程可组装，且组装期校验**：控制流程不靠"某段代码里的隐式顺序"，而由**装配层显式组装**——可组装的件是四张清单：**原语清单**（工具面及顺序）/ **两段提示词插件**（system 与 user 的正文拼接顺序）/ **结果过滤器链**（工具结果的加工顺序）/ **三组 handler**（循环前、轮边界、循环后各一组）。每张清单的**顺序即语义**。**组装必须在启动期成立**：缺件（模型、工作区、装配参数）或就绪失败（基线取不到、工作区不可用）一律在**首轮推理之前**失败（退出码 1），不允许跑到一半才炸。见 `xhunter-architecture.md` §4 与 §6 |
| FR-1.9 | **支持多形态驱动**：核心可被①**配置驱动**（外部生成 Bounty 并投递）②**观察驱动**（外部消费事件流做展示）③**单步驱动**（进程内逐阶段推进）三种形态驱动。**①与②不需要核心改动**（协作方皆接口、装配只在组装层）；**③不进一期**。**硬要求：任何形态都走同一份装配**——外部不得自建一条执行路径，否则它就会成为绕过不变量的后门：基线先于任何写操作、写盘唯一入口、终态必上报，这些不变量都落在装配与初始化顺序里。设计见 `xhunter-architecture.md` §5 |
| FR-1.10 | **驱动者无关性 + Bounty 自举**：任何能"准备 Bounty 文件 + 启动进程 + 消费 stdout 事件流"的实体都是合法驱动者（平台 daemon 只是其中之一；**本地运行的 UI/脚本同样合法，无需核心改动**）。为此补齐**Bounty 生成能力**：给定本地仓库路径 + 任务描述，探测 `remote` / 基线 commit（取 HEAD）/ 任务分支名 / 门禁候选（仓库根 `gates.yml` 存在性）/ 预算与策略默认值，生成 Bounty 文件。**边界**：① 生成器**必须 clone 到临时工作区**，不得把用户当前仓库目录当工作区（§3 硬约束，且会污染用户的未提交改动）；② 生成过程**不得放松任何不变量**——门禁来源、凭据要求（需写权限）、模型无 git 能力一律不变；③ 生成器只是**便利工具**，不进入交付路径（平台仍可自行生成 Bounty）。**它同时是澄清回路的入口**：人照着结果文件里的 `needs` 补条件、生成新 Bounty、带同一 session 重投（见 §3） |
| FR-1.11 | **运行段看护（4 条）**：① **流看门狗**——接收段不活动超时（`StreamIdleTimeout`，默认 120s）即 Cancel 并以环境错误收敛，流内挂起时长必须有上界（实现状态见 xhunter-status.md 状态索引 · FR-1.11）；② **提交连败提前收敛**——检查点连续失败达上限（3 次）后，**本轮结束即进入终态收敛**，不跑完剩余轮次（实现状态见 xhunter-status.md 状态索引 · FR-1.11）；③ **取消衔接**——收流中途取消时，已收未执行的工具调用不执行，本轮按"已执行部分"配对落盘并标注 `cancelled`；④ **工具面定格**——模型可见工具面（**工具名集合 ＋ 各自参数 schema**）在初始化阶段一次性定格（构造原语后写入本轮请求的工具面），此后整任务读同一份（单一事实源），不各自推导。**工具名在同一构建内不增减、随能力接入而扩展**（FR-4.11）：符号原语的**可用性**由扩展能力决定，但它只影响**调用结果**，不影响工具面 |

> **为什么"可组装"不以牺牲不变量为代价**：不变量不再靠"这段顺序没被人改过"，而靠**装配顺序与初始化顺序**——"取基线必须是初始化的第一步"（INV-11）、"落盘只能走唯一写入口，且执行在轮边界、提交紧随其后"（FR-1.3c、INV-10）、"取消与预算检查必须存在"（INV-3、FR-9.2）、"收尾必跑交付提交与终态上报"（§3）。落点见 `xhunter-architecture.md` §4 的不变量落点表。

### FR-4 符号级编辑

以语法解析为基础，把编辑目标从"一段文本"升级为"一个符号"。

**交付形态**：本节能力**不在核心二进制内实现**，而是以 MCP 扩展接入（见 FR-13）。核心保持语言无关、不内嵌任何语言的解析器；解析器与语言语法属于扩展侧，其选型不影响核心。

| 编号 | 需求 |
|---|---|
| FR-4.1 | **阶段一（只读）**：支持符号枚举与按符号读取，不涉及任何写回 |
| FR-4.2 | **阶段二（整体替换）**：支持按符号限定名整体替换符号体 |
| FR-4.3 | **阶段三（精细手术）**：支持在符号内指定位置插入，以及跨文件重命名符号 |
| FR-4.4 | **不变量：区间替换**。写回必须只改写目标符号的字节区间，其余字节原样保留。**禁止重新打印整棵语法树**，否则注释、空行与格式会被整体洗掉，产生无法 review 的巨型 diff |
| FR-4.5 | 源码存在语法错误时（含 `ERROR` 节点）必须能检测并降级到文本替换模式，给出显式提示而非失败 |
| FR-4.6 | 写入代码需按目标位置的缩进层级重排，并探测目标文件的缩进风格（制表符/空格、宽度） |
| FR-4.7 | 符号级编辑必须是文本编辑的超集。对无语法定义的文件类型（配置文件、模板、`.env` 等）自动使用文本模式 |
| FR-4.8 | 编辑失败必须以结构化错误返回（目标不存在、歧义、解析失败），便于模型自愈 |
| FR-4.9 | **不限开发语言**：能力选择不得因语言未支持而拒绝仓库或文件。任何语言的仓库都必须可被受理与完成，最低以文本路径运行（对应语言中立原则） |
| FR-4.10 | **语言注册机制**：**符号原语的可用性**由语言注册表驱动——已注册语言使符号原语可用；未注册语言使其返回结构化错误（**基础原语不受影响**）；新增语言不得改动上层工具契约（FR-4.11、FR-13.2） |
| FR-4.11 | **工具面恒定（同一构建内恒定、随能力接入而扩展）**：**符号能力以工具名体现**：符号形态各占一个原语名，模型用"选哪个工具"表达寻址意图；语义上它们是基础原语的符号寻址版本，实现上先定位到字节区间、再复用基础读写（§6）。**工具面在同一个构建版本内恒定**：**环境能力不决定注册**——扩展不可用、语言未注册只改变"调用时会发生什么"（退回文本行为 / 返回结构化错误），不改工具名与参数 schema。**工具面随能力接入而扩展**：尚未实现、且不在本次构建范围内的原语**不注册**（模型看不到它），实现落地后再注册。**当前构建工具面 = 9 + 1**：`read` / `write` / `edit` / `find` / `glob` / `check` ＋ 三个符号原语（`symbol_read` / `symbol_edit` / `symbol_rename`，已随 MS-8 / MS-10 注册），加执行体殿后追加的 `checkpoint`。注册规则见 §6 |
| FR-4.12 | **寻址规则**：寻址方式由**模型选原语**表达（文本原语 vs 符号原语）；符号原语是否可用由"语言已注册且语法可解析"决定，**不可用时返回结构化错误并如实上报，不静默改用文本替换**。**两条路径都不得放宽匹配语义**：内容寻址的唯一性校验、符号寻址的定位失败，都必须显式报错（对齐 FR-4.4、FR-3.2） |
| FR-4.13 | **寻址可观测**：每次调用在工具结果与事件流中如实上报**所用寻址**（由工具名体现）、**精度等级**（syntactic / semantic）与不可用/降级原因，供远程诊断与命中率统计（对齐 FR-11.2、FR-11.5）。**不得把语法级结果当作语义级呈现** |

### FR-5 自检（验）

| 编号 | 需求 |
|---|---|
| FR-5.1 | 写入后必须读回变更内容，确认无截断与语法残缺 |
| FR-5.2 | 支持运行**受限校验命令**（白名单机制，如类型检查、静态检查、项目声明的校验脚本）。准确表述是：**不提供任意命令执行，提供的是对受审命令集合的"具名调用"**——模型只给门禁名（枚举），命令来自受审配置，`argv` 固定（FR-5.2b）。**实现不需要 shell**：`argv` 数组直启（fork+exec），超时/截断/非交互一律走内置实现，不调用 `timeout`/`head` 等外部工具 |
| FR-5.2b | **质量门禁是 `check` 原语的具名条目，不是新工具**：清单字段为 `name` / `argv`（数组直启不经 shell，**`argv[0]` 为 `sh`/`bash`/`zsh`/`dash` 一律拒绝**）/ `timeout` / `required` / `expect`（通过判据）/ `dir`（工作子目录，monorepo 需要）/ `env`（**显式声明的环境变量**，见 FR-5.2i）。**有三个来源，按优先级**——① **Bounty 下发**（平台显式配置，可覆盖/禁用仓库声明）② **仓库声明**（仓库根的 `gates.yml`，**从基线 commit 读取**，见 FR-5.2g）③ 都没有则不设门禁（`required` 为空 → 无"未运行即失败"约束）。**`expect` 必须可表达"非退出码"判据**（如 `gofmt -l` 的"输出为空"），否则格式门禁永远"通过"。`expect` 是一个对象：<br>· `kind`（**必填**）：`exit_zero` ｜ `empty_output` ｜ `regex` ｜ `max_count`<br>· `pattern`（`kind` 为 `regex` / `max_count` 时必填）：**RE2 语法**（Go `regexp` 包；不支持环视与反向引用——写清单的人要知道这一点）<br>· `max`（`kind=max_count` 时必填）：匹配次数的上限<br>· `stream`（缺省 `stdout`）：`stdout` ｜ `stderr` ｜ `both`<br>**判定语义**：`regex` 是**找到至少一处匹配即通过**（不做全文匹配，避免锚点歧义）；**所有判据都在"全量输出"上计算**——交给模型的输出会按 FR-5.3 截断，**截断不得影响判定**（"输出为空"必须看全量，否则截断会造成误判）。`kind` 必填是刻意的：忘了写就默默按退出码判，是最危险的静默失败。门禁名注入上下文供模型调用。结果（名称 / 通过与否 / 是否命中缓存）进事件流与结果文件——它是 MR 评审最需要的证据。设计见 `xhunter-architecture.md` §7.3 |
| FR-5.2c | **门禁驱动的检查点**：门禁**通过**即立刻产生一个检查点（最强的"自洽状态"信号，FR-1.3c）；门禁**未通过**则抑制后续自动检查点，直到下一次通过或收尾交付——**破损状态不被钉住** |
| FR-5.2d | **门禁执行失败与判定不通过必须区分**：命令不存在 / 无法创建进程 / 超时 = **环境错误（退出码 1）**，不是质量结论；退出码非 0 或输出越阈值 = 质量不达标（终态失败，若 `required`）。任一 `required` 门禁未通过**或从未运行** → `status=failed`（**退出码仍为 0**：对话正常走完，失败由证据给出），但改动照常交付（FR-6.5） |
| FR-5.2e | **门禁结果缓存**：按待提交改动的内容指纹缓存，同一状态重复调用返回缓存（标注 `cached`）。避免重复执行耗时的测试命令，也避免重复门禁调用产生重复检查点 |
| FR-5.2f | **门禁的执行主体（分两层）**：<br>· **主路径 = 模型通过 `check` 工具调用**——模型判断"何时值得验证"（改完一批相关文件之后，而非每次编辑），门禁通过即触发检查点（FR-5.2c）<br>· **兜底 = 收尾前自动补跑 `required` 门禁至少一次**——判据是**证据**：`required` 门禁从未运行意味着这次交付没有质量证据，照判失败（FR-5.2d）；而收尾时的工作区正是**最终交付物**，此时跑出来的结论才有针对性<br>两层都受同一策略框架约束：命令来自 Bounty 白名单、argv 直启、非交互、超时（FR-8.6）。自动补跑遵守墙钟预算——预算已耗尽则不再补跑，按"未运行"判失败 |
| FR-5.2g | **仓库声明的门禁清单在仓库根 `gates.yml`，从基线 commit 读取**（`git show <base_commit>:gates.yml`），不从工作区读取。两点说明：① **位置**——它是**仓库级配置，不是引擎私有文件**（别的工具也可以读它），因此不放进 `.xhunter/`；② **理由不是"防谁篡改"**，而是**判据必须在运行开始前定死**：门禁是这次交付的验收标准，让它运行中途变，这次结论就不可复现。**不限制模型修改该文件**——改动照样进交付 diff 由人 review，只是本次不生效（要本次生效必须由 Bounty 授予 `gates_source: working_tree`，见 FR-5.2h） |
| FR-5.2h | **任务本身是改门禁时**：默认"从基线读取"意味着新清单**本次不生效，下次成为新基线后才生效**（与 CI 惯例一致）。需要新清单本次生效时，**只能由 Bounty 显式授予**（`gates_source: working_tree`），并受三条护栏约束——**元门禁**（schema 合法 + 每个 `argv` 可启动 + **`expect` 可判定**：`kind` 已知、所需字段齐备、`pattern` 能被 RE2 编译——任一项不成立即**启动期拒掉这份清单**，而不是运行到门禁执行时才炸）、**强度不得降低**（同名 `required` 门禁的 `argv`/`expect` 不得改动，只允许新增）、**显式上报**（`gate_config_changed` 事件 + 结果文件标注清单来源）。清单文件本身**不限制模型写**，因此**三条护栏在豁免生效时是唯一防线**。**模型拿不到豁免**：`gates_source` 只存在于 Bounty（Harness 的输入），模型既看不到也改不了 |
| FR-5.2i | **门禁子进程的环境与凭据隔离**：① **Xhunter 自身凭据（git 推送用）绝不得传给门禁子进程**——否则任何测试脚本都能读到并外泄（FR-8.4 的延伸）；② 传给门禁的环境 = 最小集（`PATH`/`HOME`/`LANG`/`CI=1`/`NO_COLOR=1`/`GIT_TERMINAL_PROMPT=0`）+ **清单里显式声明的 `env`**；③ 若某门禁确实需要凭据（如集成测试的数据库连接串），由**平台在 `env` 中显式给出**，并计入 FR-8.4 的"不得进入上下文/事件/交付物"约束 |
| FR-5.3 | 校验命令的输出需截断至合理长度并结构化为事件上报，避免污染上下文 |
| FR-5.4 | 结束前需对新引入符号做一致性检查：是否已定义、导入是否齐全、调用签名是否匹配 |
| FR-5.5 | 产出 patch 前需自审 diff，检出误删、调试残留、无关格式变更 |

### FR-6 交付

| 编号 | 需求 |
|---|---|
| FR-6.1 | **主交付**：任务分支上的提交链（阶段性检查点，交付 = 分支 tip，见 §3）；**附带交付**：相对基线的统一 diff（`git apply` 兼容，`git diff <base>..<tip>`），**排除会话材料路径 `.xhunter/<session_id>/**`**（按任务隔离；门禁清单等其他路径不排除），附基线 commit 与分支 tip SHA |
| FR-6.2 | 产出变更说明：改了什么、为什么、影响哪些文件与**改动规模**（文件数 / 处数）——没有人类 review 时，这些数字是下游判断"能不能继续往下自动化"的证据。**变更说明与最终结论都由模型的最后答复给出**，它必须进事件流（`assistant_text`）与会话材料，并在结果文件里以 `summary` 落一份快照——**任务可能只要这份小结**，它不能被当作噪音丢掉 |
| FR-6.3 | **产出两类清单**：① **需要补全的清单**（`needs`）——**任务描述与项目约定都没有给出**的必要事实，逐条说明「缺什么、为什么不能取默认」；它替代运行期追问，由**投递层**接住（人补齐条件 → 新 Bounty ＋ 旧 session 续跑，见 §3「澄清回路」）。② **假设清单**——信息不足时采取的最保守默认，逐条列出。判据来自**任务描述与系统提示词**：那里已经给出的，不得再列为「缺」 |
| FR-6.4 | 标注不确定项与未覆盖风险，供下游聚焦——无人 review 时，它决定这次交付能不能自动往下走 |
| FR-6.5 | 若校验未通过，改动仍应交付（提交照常推送）但状态必须为失败，不得静默降级为成功 |

### FR-7 首轮提示词与组装

首轮固定为 `system` 与 `user` 两条消息，与协议首轮消息一一对应：前者放稳定内容（利于前缀缓存），后者放本任务的动态内容。**两段正文都由插件贡献**（FR-7.8）。

| 编号 | 需求 |
|---|---|
| FR-7.1 | 两段职责不混：**system 段** = 内核条款 + 项目约定与技能清单；**user 段** = 环境事实 + 任务描述 |
| FR-7.2 | 必须包含**无人类条款**（由内核拼入 system 段末尾，插件删不掉也改不动）：禁止提问、禁止请求确认、禁止等待输入，**也不得请求权限**——无人值守下没有这条路径，裁决只出自策略（INV-4） |
| FR-7.3 | 必须包含**止损规则**（同上）：同类失败达到阈值后换策略，仍失败即失败退出；预算不足立即失败，不得绕过 |
| FR-7.4 | 完成标准必须是可验证的（目标行为实现 + 通过既有校验 + 产出可应用 patch），不接受"尽力而为" |
| FR-7.5 | 环境事实（工作目录、平台、shell、包管理器、基线 commit、dirty 状态）必须运行时注入，禁止在模板中写死；**由内核注入 user 段**——这些是内核知道而插件无从知道的事实，交给插件陈述就会在换机器、换平台之后继续断言旧事实 |
| FR-7.6 | 按缓存友好顺序组装：稳定内容进 system 段，动态内容进 user 段 |
| FR-7.7 | 能在工具 schema 中表达的信息不得在提示词中重复描述 |
| FR-7.8 | **组装过程是扩展点**：两段正文由**多个插件**贡献、按**装配顺序**拼接（同一插件可同时挂在两段上）。约定文件如何发现、技能清单从哪来、正文写什么，全部由插件决定，内核不规定位置与格式。内核保留四条职责：**两段的位置与顺序**（插件给正文，不给消息序列）、**取一次并冻结**、**内核条款在 system 段末尾追加**、**不得越界**（正文改变不了工具面、策略裁决、路径边界与凭据边界） |
| FR-7.9 | 插件附带义务：单条素材非法（如一份写坏的技能说明）**跳过而非整体失败**，并**经事件流上报**降级；构造失败（基线读不了、扩展不可用）→ 退出码 1。少了系统提示词与项目约定而继续跑，产出只会慢慢偏出仓库约定，且没有任何一步会报错 |

### FR-8 策略与安全边界

无人类审批通道，**策略引擎即权限边界本身**。

| 编号 | 需求 |
|---|---|
| FR-8.1 | 读操作默认可行，但受工作区路径限制（FR-3.5） |
| FR-8.2 | 写操作受路径约束；工作区外的任何写入一律拒绝 |
| FR-8.3 | 禁止破坏性操作：递归删除、强制推送、硬重置、修改持续集成配置。**推送只允许 fast-forward**（远端 tip 必须是本地父提交）：推送到其他分支、改写已推送历史、删除分支一律拒绝 |
| FR-8.4 | 凭据只从环境变量注入，**不得进入模型上下文、日志、事件流与 patch** |
| FR-8.5 | 策略拒绝必须以结构化事件上报（被拒操作、拒绝原因），不得静默跳过 |
| FR-8.6 | 涉及需要交互确认的外部命令（版本控制、包管理器等）必须设置非交互环境变量，并对子进程关闭标准输入 |
| FR-8.7 | **原语级策略粒度**：策略必须能按「原语 ＋ 参数（路径）」分别裁决与拦截（例如允许 `read`、拒绝 `symbol_rename`）；拒绝行为须结构化上报（FR-8.5）。**不按改动规模设阈值**：无人 review 的终局要求判据来自证据，"改得多就保守拒绝"是偏好而非判据——改动规模只**如实上报**，不作拦截依据 |

### FR-9 预算与止损

| 编号 | 需求 |
|---|---|
| FR-9.1 | **三重预算上限：模型 token、推理轮数、墙钟时间——三项都是可选的，不配就是不限制**（同一台机器上往往只有部分维度需要设限，硬要求全配只会逼出随便填的数字）。投递层把「不配」与「配错」分得很清：**不配 = 该维度不限；显式写 `0` / 负数 / 非法值 = 启动期失败**——「以为设了限制、其实没有」是最危险的静默失效 |
| FR-9.2 | 任一预算耗尽立即终止，状态为失败并上报耗尽维度（**未设限的维度不参与判定**——不设就是不限，不是默认值） |
| FR-9.3 | 不允许任何形式的预算绕过或自动延期。**不设上限 ≠ 可以绕过上限**：不设 = 该维度没有止损，设了就必须遵守 |
| FR-9.4 | 连续同类工具失败达到阈值触发策略切换，超过上限即失败退出 |
| FR-9.5 | **上下文窗口上限必须由投递给出**：`XHUNTER_MODEL_CONTEXT_TOKENS` 必填，运行时**不得估算**。它与其他模型接入事实（协议、端点、凭据、输出预留）一样走环境变量——**没有配置文件、没有内置目录、没有合并与回退**；缺失即**启动期显式失败**（退出码 1，环境问题可重试），不得以隐式默认值继续。变量清单见 `xhunter-usage.md` §3 |
| FR-9.6 | **压缩水位线与可用输入预算由接入事实推导**：可用输入预算 = `XHUNTER_MODEL_CONTEXT_TOKENS` − 固定开销（system 段 ＋ 工具 schema）− `XHUNTER_MODEL_OUTPUT_TOKENS`；水位线默认 预警 70% / 目标 50% / 硬上限 90%（以可用输入预算为基数）。参数可配置但必须有默认值 |
| FR-9.7 | **用量不可得时不得估算**：上游未回报用量（网关不支持 `include_usage` / 流中断）时**不做本地估算**——如实在事件流（`degraded`，`scope: "usage"`）与结果文件（`usage.reported: false`）里标注「用量不可得」。**不得用拍出来的数字去触发或不触发 token 预算**：宁可让平台知道"这次没有 token 止损"，也不要一个假数字 |

> **上限类字段不得估算，行为类字段可降级**：`MaxContextTokens` 属前者——估算偏高会在任务中途触发硬失败，估算偏低会静默损害所有同类任务；启动期一次性显式失败，把问题暴露在任务开始之前，且退出码 1 的语义（环境问题可重试）正好承接"修好配置后重派"。而**用量不可得时不许估算**（FR-9.7）：上游不回报就如实标注，宁可说"这次没有 token 止损"，也不要拍一个数字去决定停不停——估算值会污染硬止损。

### FR-10 状态输出与心跳

外部通道只有一条：**stdout 事件流**（FR-1.4）。因此本节的"输出"一律指写入该通道，不涉及网络上报。

| 编号 | 需求 |
|---|---|
| FR-10.1 | 运行期间按固定间隔输出**任务级**心跳事件，与 runtime 心跳完全解耦。间隔**默认 30s**，`XHUNTER_HEARTBEAT_INTERVAL`（Go duration）可覆盖——任务时长差很多；没有间隔上限就只有一个很小的默认值，长任务里会把事件流刷满 |
| FR-10.2 | 终态必须显式输出事件，不允许仅依赖退出码。**终态 `status` 由模型在最后答复里声明**（取值域由 Xhunter 定义：`succeeded` / `blocked` / `failed` / `cancelled`；**何时给哪个由平台的系统提示词决定**）；引擎如实采纳、不替模型下结论——只有机制性终止（取消、预算耗尽、推理失败）与客观证据（`required` 门禁未过）才由引擎强制给出。**退出码只表达"这一趟是怎么结束的"**（0 模型正常完成对话 / 1 环境问题 / 2 被引擎中止 / 3 取消），不表达任务成败 |
| FR-10.3 | 心跳需携带当前阶段与已用量，供平台侧判断"运行中"与"卡死" |
| FR-10.4 | **通道断裂即终止**：事件（含心跳）**写入失败时记录并终止**，不得静默丢弃进度、不得假装仍在工作。stdout 是唯一通道，写失败意味着消费者已不在（EPIPE）或无法接收（磁盘满），属**环境问题，退出码 1**——平台可修好后重派 |

### FR-11 可观测与远程诊断

| 编号 | 需求 |
|---|---|
| FR-11.1 | 每次模型调用与工具调用均产出结构化事件，含耗时与用量 |
| FR-11.2 | 错误必须结构化：错误类型、上下文、是否可重试 |
| FR-11.3 | 全流程携带统一追踪标识，可串联平台侧记录 |
| FR-11.4 | 人类可读日志与机器事件流分离输出（事件流走 stdout，日志走 stderr） |
| FR-11.5 | 因无人查看终端，所有失败信息必须自含足以远程定位的上下文 |
| FR-11.6 | **生效配置快照**：启动时产出一份"本次 Hunt 实际生效的规则"快照——**装配清单**（原语清单与顺序、两段提示词插件与顺序、结果过滤器链）、**门禁清单**（含**来源**：Bounty / 仓库声明 / 豁免）与各自 `required`、策略配置、预算上限、检查点行为、扩展能力指纹、目标平台。**进 `hunt_start` 事件并写入结果文件**。它同时服务远程诊断（FR-11.5）与 MR 评审（"这次验收用的是什么规则"），且**只读快照、不可由模型影响** |

### FR-12 幂等、清理与会话恢复

| 编号 | 需求 |
|---|---|
| FR-12.1 | **会话恢复（resume）**：投递给出 `XHUNTER_SESSION_ID`（= 延续一个既有会话）时进入续跑——分支与记忆都以会话标识为准（`xhunter/<session_id>`、`.xhunter/<session_id>/`），因此接的是同一条分支、同一份历史——clone/fetch 仓库 → checkout **任务分支 tip（最后一个检查点）**，该状态即上次工作区 → **读回会话材料**（`.xhunter/`，随检查点提交、由 git 保证完整性）→ 回灌上下文后继续推理。**不重放写操作**：上一个检查点之后的改动由模型在续跑轮自然重做（代价有界：最多一轮）。**resume 有两个触发场景**：① 崩溃/换机后的 failover（AC-7）；② **澄清后继续**——人补齐条件后带同一 session 重投，**补充的条件作为新的 user 消息追加在回灌历史之后**，模型因此看到「上次列了什么问题、这次给了什么答案」 |
| FR-12.2 | 会话材料自含续跑所需信息：对话历史（含每次工具调用与结果摘要）、写操作序列、turn 序号、用量。**随检查点提交进任务分支**，格式自描述且带 `schema_version` |
| FR-12.2b | **材料按任务隔离**：路径为 `.xhunter/<session_id>/session.jsonl`——**每个任务一个独立文件**。因此同一仓库多任务并行时各写各的材料，不存在交叉覆盖。**材料体积有上限**（FR-12.2c）。**同一 Bounty 不并行执行**（一任务一分支一进程）；若平台违规并行，两端都会因 fast-forward 推送失败而**显式报错**，而不是静默冲突（FR-8.3） |
| FR-12.2c | **材料体积上限**：超过阈值（默认 2 MB）时**丢最早轮次的原文**，但**写操作记录与最终答复永不丢**——FR-14.3 的「永不丢」清单不因超限而松动；丢弃动作**如实上报**（`degraded`），不静默 |
| FR-12.3 | **会话材料不可被模型篡改**：① 模型无 git 操作能力（INV-11），无法改写已提交历史；② 策略层禁止模型写入 `.xhunter/**`（FR-8.7 路径级策略）；③ 该路径不参与交付 diff（FR-6.1，排除范围即 `MaterialDir`）。**提交时必须强制加入**（`add -f`）——若仓库自身的 `.gitignore` 恰好忽略 `.xhunter/`，静默跳过会导致材料未随分支提交、续跑失效 |
| FR-12.3b | session 增量随事件流周期性落盘，与关键状态落盘同源，应对无法捕获的强杀信号 |
| FR-12.4 | 退出时必须回收全部子进程、临时目录与文件锁 |
| FR-12.5 | 清理失败不得阻断退出流程，但必须记录 |
| FR-12.6 | **恢复失败**（会话材料损坏或版本不兼容、任务分支不可达、checkout 失败）时显式失败，退出码 1，由平台 fallback 到干净基线重跑；resume 是优化，重跑是兜底，两者不互斥 |

### FR-13 扩展接入（MCP）

符号级能力以 **MCP 扩展**形式提供，核心不含解析器与语言语法。

> 本节讲的是**能力扩展**（给工具加后端）。**内容扩展**（提示词正文、项目约定、技能清单由谁提供）是另一回事，见 FR-7.8——两者都叫扩展，但前者扩展工具的能力面，后者只贡献文本，改不了工具面与权限边界。

> 本节讲的是**能力扩展**（给工具加后端）。**内容扩展**（提示词正文、项目约定、技能清单由谁提供）是另一回事，见 FR-7.8——两者都叫扩展，但前者扩展工具的能力面，后者只贡献文本，改不了工具面与权限边界。

| 编号 | 需求 |
|---|---|
| FR-13.1 | 支持以 MCP 接入本地扩展进程（stdio 传输）；核心不因扩展存在与否改变可用性 |
| FR-13.2 | **扩展不新增工具名**：扩展的能力通向**已注册的符号原语**，它不带来新工具名、也不改参数 schema（FR-4.11、§6）；扩展结果与内置结果在结构、错误语义上完全一致 |
| FR-13.3 | **写入落盘集中在核心**：扩展不直接写工作区，只返回定位结果（目标文件 + 字节区间 + 新内容），由核心执行区间替换。单一写入原语（FR-4.4）不因扩展而分裂 |
| FR-13.4 | 扩展缺失、启动失败或超时：**符号原语**不可用——**工具不撤回**（仍注册，FR-4.11），调用返回结构化错误；基础原语（文本寻址）不受影响。模型收到**显式提示**（如"请改用 `edit` 做文本替换"），任务不失败（对齐 FR-4.9、FR-4.10、AC-11、AC-26）。**时机区分**：符号原语的**注册**随 MS-8 接入；**接入之后**扩展不可用仍不改工具面，只改调用结果（接入之前这三原语根本不注册） |
| FR-13.5 | 扩展进程生命周期：懒启动（首次调用符号工具时拉起）、随 Hunt 退出回收（FR-12.4）；扩展崩溃可隔离，不得使主循环静默挂起（INV-3）。**注册即副作用、卸载即撤销**：扩展注册的一切（工具 schema、符号定位能力、能力描述符）随其卸载**全部撤销**，不留悬挂状态（对齐 INV-3） |
| FR-13.6 | 扩展处于**不可信边界**：仅允许本地进程；不得接触凭据（FR-8.4）；路径校验与写盘仍由核心执行，扩展无法绕过 FR-3.5 / FR-8.2 |
| FR-13.7 | 会话材料须含**扩展能力指纹**（扩展标识 + 版本 + 覆盖语言清单 + 后端与精度等级），**用于诊断**：能力变化可能解释"续跑后的精度与上次不同"。**不再作为重放闸门**——检查点恢复不依赖重放，故指纹不一致只记录、不阻断 |
| FR-13.8 | **后端抽象**：扩展**内部**以"能力声明驱动的后端抽象层"实现符号能力，后端可替换（自包含语法解析后端 / LSP 语义后端 / …）。核心不感知后端种类，只消费**能力描述符**（能力集 + 精度等级），据此决定符号路径可用性与结果标注 |
| FR-13.9 | **外部后端不得成为必需依赖**：依赖外部进程的后端（如 LSP 需按语言安装语言服务器）为可选后端，缺失时降级到自包含后端并**上报精度变化**（对齐 NFR-1、FR-13.4） |
| FR-13.10 | **协议托管 MCP 不采用**：OpenAI Responses 的内置 `type:"mcp"` 工具与 Anthropic Messages 的 `mcp_servers` 连接器把 MCP 客户端搬到**供应商侧**——工具由上游代跑、结果直接进上下文。它绕过策略裁决（上游调用不经 Policy）、绕过唯一写盘入口（工具执行永远在 Harness 侧），且仅支持公网 HTTPS 服务端（无法接本地 stdio 扩展）、凭据须交给上游。本项目的 MCP 仅限本地 stdio 扩展（FR-13.1、FR-13.6）；线格式包不发送也不消费这些字段（上游加字段按容错处理，不致解析失败） |

### FR-14 上下文压缩

| 编号 | 需求 |
|---|---|
| FR-14.1 | **水位线触发**：窗口按预警（默认 70%）触发压缩、目标（默认 50%）为压后水位、硬上限（默认 90%）视为不可继续。**不允许"超限才压"**——届时已无余量执行压缩后的那一轮推理。压缩后需有冷却期（**默认 3 轮**），防止震荡 |
| FR-14.2 | **分层压缩**：L0 工具输出截断 → L1 丢弃可重建信息（推理过程）→ L2 工具输出整体替换为可寻址摘要 → L3 旧轮折叠为结构化工作日志 → L4 模型摘要（可选）。按序下压，够用即停 |
| FR-14.3 | **保丢优先级**：永不丢——Bounty 正文与验收标准、工作区约定、当前轮 messages、**写操作记录**、**最终答复（终态声明与结论）**；优先保留——最近 N 轮的完整调用/结果对；可替换——早期工具输出；可丢弃——推理过程、重复失败细节、已被覆盖的中间态 |
| FR-14.4 | **确定性优先**：默认压缩**零模型调用**。结构化工作日志由 session 记录**投影**生成（FR-12.2），内容与顺序均可复现 |
| FR-14.5 | **模型摘要为可选最后手段**（L4）：**默认不启用**（确定性优先，FR-14.4）；启用后须计入 token 预算（FR-9.1），且摘要文本**生成一次即落盘**、恢复时读回——不得在**恢复路径**上重新生成（对齐 FR-12.1） |
| FR-14.6 | **交付物不依赖上下文**：patch、变更文件清单、假设清单与未覆盖风险一律由 Harness 从 session 记录生成，不得依赖模型对压缩后历史的回忆 |
| FR-14.7 | **可观测**：每次压缩产出结构化事件，携带命中层级与释放的 token 量，供平台侧判断任务效率是否退化（对齐 FR-11.1、FR-11.5） |
| FR-14.8 | **恢复回灌走同一管线**：resume 时的上下文回灌使用与正常运行时相同的压缩规则，不做特殊处理；历史低于阈值则全量回灌 |

### FR-15 Skill 渐进式加载

| 编号 | 需求 |
|---|---|
| FR-15.1 | **格式对齐开放标准**（[agentskills.io](https://agentskills.io) 规范）：skill = 一个目录 + `SKILL.md`（YAML frontmatter：`name`（必填，1-64 字符小写字母/数字/连字符，须与目录名一致）+ `description`（必填，≤1024 字符）），可含 `references/`、`scripts/`、`assets/` |
| FR-15.2 | **三层渐进披露**：**发现**——启动时由提示词插件（FR-7.8）扫描 frontmatter，向 system 段注入"可用 skill 清单"（name + description，~100 token/条）；**激活**——模型按需以 `read` 原语读 SKILL.md 全文（<5000 token）；**执行**——references/ 等素材同样经 `read` 按需读取。全程**零新原语**（工具面不变），前端清单只是上下文组装的一次性注入 |
| FR-15.3 | **来源与冻结语义**：目录位置属**默认插件**的约定（工作区内 `.xhunter/skills/`（不进交付 diff，随会话材料排除；策略禁止模型写）。清单与内容**从基线 commit 读取**（内核保证构造一次即固定）——与门禁清单同一语义：冻结配置、防模型中途改；`dir` 档（任意目录工作空间）下退化为文件系统读取并在结果中标注来源。**激活面只认基线冻结版**：模型可将新 skill 写入 `.xhunter/skills.draft/` 起草面（普通工作区路径，进交付 diff 由人 review），但正在执行的 agent 不得改完规则立刻按新规则继续跑；跨任务 skill 演化 = "模型起草 → 交付 diff → 人合并 → 成为下次运行的新基线" |
| FR-15.4 | **不做执行面**：`scripts/` 一期**不可执行**（工具面里没有任何 shell 能力，skill 不得成为绕过通道）；frontmatter 的 `allowed-tools` 字段**忽略**——素材不得自我授权（INV-4：权限裁决只出自 Policy） |
| FR-15.5 | **解析容错**：只解析 frontmatter 的 name/description 平面标量；格式非法的 skill 跳过并在事件流上报（可观测降级，对齐 FR-13.4 精神），不阻塞任务 |
| FR-15.6 | **预算护栏**：发现清单有总量上限（建议 ≤50 条 / 溢出截断并上报）；SKILL.md 读取走通用截断（FR-2.1）与 L0~L4 压缩（FR-14），无豁免 |

### FR-16 模型接入（协议适配器）

| 编号 | 需求 |
|---|---|
| FR-16.1 | **模型调用一律经 Provider 适配器**：编排逻辑（循环、工具、上下文、策略）不认识任何具体协议与供应商；适配器是唯一知道"怎么与某个端点说话"的地方 |
| FR-16.2 | **协议实现与装配分离**：协议实现只说协议——入口是普通构造函数，只接受已解析的连接事实（端点、模型、鉴权头值、上限），不含"自己叫什么名字"的装配知识，也不做注册；**哪个协议取值对应哪一种协议实现，由组装层决定**。接一种新**协议** = 加一个协议包并在组装层加一行绑定；接一家新**厂商** = 设置一组环境变量，协议实现、Harness 与组装层代码都不动 |
| FR-16.3 | **一个协议一个包**：协议实现之间互不引用；共用件（流式分帧、中立调用词汇、协议侧错误形状、上限契约）下沉到共用包，因此改一家不牵动另一家。协议包不依赖配置模型，可脱离本项目的配置体系被独立复用 |
| FR-16.4 | **协议事实不外泄**：请求形状、流式分帧、增量拼装、错误分类与可重试性判定都在适配器内，上游线格式类型不导出；Harness 侧只出现协议中立的消息、工具声明与事件 |
| FR-16.5 | **接入失败发生在启动期**：模型上限缺失、端点缺失、`XHUNTER_HEADERS` 里的凭据引用解析为空、组装层没有该协议的适配器 → 显式失败（退出码 1），不得留到运行中途——无人值守时中途失败意味着已消耗的轮次与预算全部作废 |
| FR-16.6 | **响应异常不得静默**：流中断显式上报并标注可重试性；形状不成立的调用（参数非法、工具名不认识、字段未知）带结构化错误回灌模型，既不替模型猜，也不悄悄丢弃 |
| FR-16.7 | **内置协议清单**（可扩展，不是封闭集合）：OpenAI 兼容对话补全、OpenAI Responses、Anthropic Messages。三者的共同点是"把上游协议形状关在各自包里、以中立事件对外"；差异点（消息形状、流式分帧、收尾事件、错误分类）由各自实现负责。协议取值与接入变量的语义见 `xhunter-usage.md` §4 |

## 5. 非功能需求

| 编号 | 需求 |
|---|---|
| NFR-1 | **运行时自包含**：目标环境**不需要安装任何第三方依赖库**。核心二进制把依赖在编译期静态链入，部署与执行时不要求目标环境预装语言运行时、语言服务器或 SDK；符号扩展是**独立自包含工件**（本地进程），同样不引入安装要求。**这条约束的是运行与部署，不是源码**：源码可以引用第三方库，只要不产生"目标环境必须先装点什么"的要求（判据：装好二进制就能跑）。两条边界：① 模型接入不得使用**厂商 SDK**（协议线格式手写，理由是维护面不是依赖，见 FR-16.3）；② 外部后端不得成为必需依赖（FR-13.9）。**引入第三方库的准入判据见 NFR-9** |
| NFR-2 | **冷启动可控**。单任务启动开销应显著小于任务本身的执行时间；扩展懒启动，未触及符号能力时不产生开销 |
| NFR-3 | **解析性能**（扩展侧）。单文件符号解析应在毫秒级；大文件编辑不触发全量重解析 |
| NFR-4 | **并发安全**（扩展侧）。语法解析器实例非线程安全，需按并发单元隔离；语法树只读可共享 |
| NFR-5 | **资源上限**。支持内存与临时磁盘占用上限，超限按预算耗尽处理 |
| NFR-6 | **跨平台**。支持主流操作系统，路径与换行差异需统一处理。**一期范围：仅 linux/amd64**；跨平台能力为后续阶段目标，一期须按可移植方式实现（不引入平台相关假设），但不在验收范围内 |
| NFR-7 | **体积控制**。核心不含语言语法；语法随符号扩展分发、按语言分包，不编入核心二进制 |
| NFR-8 | **可测试性**。核心能力需可在无模型参与的情况下独立测试（解析、替换、patch 生成、策略判定） |
| NFR-9 | **第三方库准入**（NFR-1 的可执行判据）。引入第三方库**允许**，但必须同时满足三条：① **纯 Go、无 cgo**——构建以 `CGO_ENABLED=0` 交叉编译到目标平台（cgo 引入 libc/动态库，那是运行期要求，正是 NFR-1 要禁的）；② **不需要运行期下载或预置数据文件**（词表、语法文件、外部可执行件）——装好二进制就能跑；③ **模型接入侧不使用厂商 SDK**（协议线格式手写，见 FR-16.3、IA-8.16(a)）。判据①可由 CI 钉住：`CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build ./...` |

## 6. 工具集规格

模型侧暴露 **9 个原语 + 1 个控制原语**，按**寻址方式**分三个领域，最后一个是不参与寻址的控制原语（**这 9 个是设计面**——"设计上有什么"；**当前构建实际注册什么**以本节的**注册规则**为准——当前 **9 + 1**，设计面已全部进入注册范围）：

| 领域 | 原语 | 寻址方式 |
|---|---|---|
| **基础** | `read` · `write` · `edit` · `find` · `glob` | 文本寻址：路径 / 行范围 / 内容字面量 / 文件名模式 |
| **符号** | `symbol_read` · `symbol_edit` · `symbol_rename` | 符号寻址：限定名 / 符号内位置（先定位到字节区间，再复用基础读写） |
| **门禁** | `check` | 具名条目（模型只给名字） |
| **控制** | `checkpoint`（殿后） | 不参与寻址，只承载"请求检查点"这一语义意图（FR-1.3c） |

> **口径变化**：早先的设计是"符号能力藏在统一原语内部、**不体现为工具名**"；现改为**符号形态各占一个原语名**。理由：工具面因此恒定且自解释——模型用**选哪个工具**表达寻址意图，不必靠参数表达方式去猜路径；代价是工具面从 5 个变成 9 个（多出的正是三个符号原语与门禁原语）。
>
> **一期实现状态**：见 xhunter-status.md 状态索引 · 产品§6。

| 原语 | 领域 | 定位 |
|---|---|---|
| `read` | 基础 | 按路径与行范围读文件（越界处标注截断） |
| `write` | 基础 | **仅新建文件**（覆盖已有文件一律走 `edit`，FR-3.2） |
| `edit` | 基础 | **内容寻址的精确替换**：按字面量匹配后替换；匹配不到或多处匹配都显式报错、不做猜测（FR-3.1、FR-4.4） |
| `find` | 基础 | 内容检索（片段 ＋ 可选的文件/目录范围） |
| `glob` | 基础 | 文件名模式匹配 |
| `symbol_read` | 符号 | 按限定名定位符号并读取其定义（可限定到某个文件） |
| `symbol_edit` | 符号 | 按限定名定位符号并替换其定义 |
| `symbol_rename` | 符号 | 跨文件重命名（一次调用完成全部改动）。**（MS-8 接入后）能力缺失时仍注册**，调用返回结构化错误（见下"注册规则"） |
| `check` | 门禁 | **具名质量门禁**（清单白名单，argv 直启不经 shell）：既是自检手段，也是**检查点的触发源**。**不是任意命令执行**——模型只给门禁名（FR-5.2/5.2b/f） |
| `checkpoint` | 控制 | **请求一个检查点**：模型提议"此刻值得钉住"，并给出语义摘要（**上限 120 字，单行**）。**不暴露分支、远端、推送目标**；提交信息由执行体合成——摘要只作素材（只取首行、剥控制字符、超长截断），前缀与分隔符固定，因此模型无法借它伪造提交结构。密度策略仍是兜底——模型不调用照常按策略提交，模型调用只是"额外提前"；**无改动则不提交**，但意图照样被消费。约束：每轮最多 1 次（FR-1.3c） |

**参数形状（JSON Schema，已定格）**：与 MCP 的 `inputSchema`、两家 function calling 的参数格式同源——一份声明原样交给任意一方，适配器只翻译信封、不碰形状。逐字发往上游，故描述从简。

| 原语 | 参数（`*` = 必填） |
|---|---|
| `read` | `path*` 工作区内相对路径 · `range{from,to}` 按行区间（1 起、闭区间；省略读全文） |
| `write` | `path*` · `content*` 完整内容 |
| `edit` | `path*` · `literal` 内容寻址的字面量 · `content*` 替换成的新内容 |
| `find` | `literal*` 检索片段 · `path` 限定文件 · `scope` 限定目录/包 |
| `glob` | `scope*` 文件名模式（如 `*.go`） |
| `symbol_read` | `symbol*` 限定名 · `path` 限定文件 |
| `symbol_edit` | `symbol*` · `content*` 替换成的新内容 · `path` 限定文件 |
| `symbol_rename` | `symbol*` 待重命名符号 · `new_name*` 新名称 · `path` 限定文件 |
| `check` | `name*` 清单里的门禁条目名 |
| `checkpoint` | `summary*` 为什么这里值得留检查点 |

两条纪律由测试守着：**schema 声明的每个属性名绑定层都必须收得下**（否则模型照说明书填的参数会被拒，而错在它看不到的地方）；**`additionalProperties: false`** 与绑定层"拒绝未知字段"是同一句话的两处表述。

> `find` 的枚举面与 `glob` **完全一致**（同一套枚举：噪音目录不可见、引擎控制目录例外）——同一条面两种用法，免得"glob 看不到、find 找得到"要靠记忆区分。

**注册规则（FR-4.11）**：**是否注册由能力接入决定**（未实现且不在本次构建范围内的原语不注册）；**环境能力不决定注册**——后者只改变"调用时会发生什么"。

| 轴 | 情形 | 行为 | 理由 |
|---|---|---|---|
| **交付分期**（**决定是否注册**） | 该能力在本次构建中**尚未实现**且**不在本次构建范围内** | **不注册**（模型看不到它）；实现落地后再注册。符号三原语（`symbol_read` / `symbol_edit` / `symbol_rename`）随 MS-8 接入时注册 | 同一构建内工具面恒定（前缀与 schema 稳定、缓存友好）；不注册是因为**模型看不到用不上的工具，不必先撞一次结构化错误**。**`check` 曾是一期的刻意不对称**——注册但返回 `not_implemented`（它是检查点的触发源）；**该形态已随 MS-5 结束**：现在是真执行器，执行器缺失是**可重试的装配缺件**（`gate_unavailable`） |
| **环境能力**（**不决定注册**） | 扩展不可用 / 语言未注册 / 不具备引用解析能力 | **恒定注册**；调用时符号原语返回**结构化错误**并显式提示，基础原语不受影响 | ① 工具面不随环境漂移；② 环境能力是**运行时**事实，不应反馈到**工具契约**层；③ 模型可据结构化错误换策略 |

判据：**工具面在同一个构建版本内恒定——环境能力不增减工具名、不改参数 schema，只改变"调用时会发生什么"；工具面随能力接入而扩展——未实现且不在本次构建范围内的原语不注册。**

**实现可替换（原语扩展点）**：注册的是**名字**，名字背后的**实现**可由装配层替换——`cmd/xhunter` 的工厂返回同一个**已知名字**但换一份实现的 `Primitive`（差量替换），或整体接管整张清单。边界与注册规则同源：只能替换**已知名字**的实现、不能新增工具名——发明新名字等于让模型可见面漂移。**框架侧只校验结构自洽、不校验业务名字**；"一期恰好这 6 个 + 1 个控制原语、顺序固定"由装配层与其测试守住。替换实现不改变模型可见的声明（名字与描述不变），因此也不影响前缀缓存。

**`symbol_rename` 的注册**：它是唯一"没有有意义降级形态"的原语——无法解析引用时，单文件文本替换是 `edit` 而非 `symbol_rename`。**一期它未注册**（装配层不交给模型，见 FR-4.11）；**随 MS-8 接入后则始终注册**——此时能力缺失**不导致不注册**，而是调用时返回结构化错误（如"当前环境不支持跨文件重命名，请改用 `edit`"），**不静默降级为文本替换**——那只会产出一个改了声明、没改调用点的半完成重命名。

**寻址规则（FR-4.12）**：

```
文本寻址（read / write / edit / find / glob）= 路径 · 行范围 · 内容字面量 · 文件名模式
符号寻址（symbol_read / symbol_edit / symbol_rename）= 限定名 · 符号内位置
  可用符号寻址 = 目标文件语言已注册（扩展可用） 且 语法可解析（无 ERROR 节点）
  不可用        → 返回结构化错误并如实上报；**不静默改用文本替换**
                  （symbol_rename 尤其如此：文本替换产出的半成品比失败更坏）
```

**四条硬约束**：

1. 寻址方式由**模型选原语**表达——用 `read` 还是 `symbol_read` 是显式选择，不靠参数表达方式去猜；
2. 两条路径都**不得放宽匹配语义**：内容寻址的唯一性校验、符号寻址的定位失败，都必须显式报错；
3. 每次调用如实上报**所用寻址**（工具名即寻址）、**精度等级**（`syntactic` / `semantic`）与不可用/降级原因（FR-4.13）；
4. **裁决先于执行与落盘**（INV-10）：策略按「原语 ＋ 参数」拦截（可表达"允许 `read`、拒绝 `symbol_rename`"，FR-8.7）；符号原语的只读定位在裁决之后进行，其算出的**改动规模只作为结果事实上报**（进变更说明与事件流，FR-6.2、FR-11.2），**不参与裁决**——不做影响面阈值。

**能力 → 原语映射**：

| 原能力 | 现归属 |
|---|---|
| 内容检索 | `find` |
| 文件的符号大纲 / 按符号读取 / 符号内相对定位 | `symbol_read` |
| 符号体替换 / 符号内插入 | `symbol_edit` |
| 跨文件重命名（含引用点更新） | `symbol_rename` |
| 内容精确替换 / 新建文件 | `edit` / `write` |
| 文件名模式匹配 | `glob` |
| 具名质量门禁 | `check` |

**明确不提供**：通用命令执行工具、网络访问、包管理器操作，以及**任何 git 操作**——分支创建、提交与推送属初始化与收尾阶段的固定职责（INV-11），**不作为工具暴露给模型**；因此也不存在"模型推到错误分支"的可能（FR-8.3 的策略规则是第二道防线，第一道是**没有这个能力**）。

## 7. 验收标准

| 编号 | 验收项 |
|---|---|
| AC-1 | 给定一个任务与干净基线，能产出可成功应用的 patch，且 patch 中不含与任务无关的格式变更 |
| AC-2 | 对包含语法错误的文件执行编辑，不崩溃、不静默失败，走降级路径并显式提示 |
| AC-3 | 对含重复模板代码的文件执行定点修改，能精确命中目标位置，且证明不会误改其他位置 |
| AC-4 | 任务信息不足时，进程不挂起等待，而是继续执行并在结果中列出假设 |
| AC-5 | 预算耗尽时立即终止并上报耗尽维度，无绕过行为 |
| AC-6 | 运行中发送 SIGTERM，进程在约定时间内退出，子进程与临时文件已清理，终态为取消 |
| AC-7 | 崩溃后重派：**平台向新机器投递同一会话**（`XHUNTER_SESSION_ID` 不变），能 checkout 任务分支 tip（最后检查点）、读回会话材料并继续推理；产出与上次检查点一致的工作区，且**未重做已完成轮次**；恢复失败时以退出码 1 显式失败 |
| AC-8 | 凭据不出现在事件流、日志、patch 与 session 记录中（需有自动化断言） |
| AC-9 | stdout 全部为合法事件行，无杂质 |
| AC-10 | 全程无任何等待标准输入的路径（静态扫描 + 运行断言） |
| AC-11 | 对**未注册语言**的仓库执行任务：能正常受理并完成，走文本模式，且在事件流与结果文件中显式标注精度降级；不出现"语言不支持"导致的拒绝或失败 |
| AC-12 | **扩展缺失/启动失败**时：任务仍能受理并完成（文本路径），事件流与结果文件如实上报扩展不可用与降级原因；核心能力不受影响 |
| AC-13 | **寻址正确性**：符号原语在"语言未注册 / 语法不可解析 / 扩展不可用"时**显式失败**（结构化错误 ＋ 不可用原因如实上报），**不退化成静默的文本替换**；基础原语在任何语言上都可用。两条路径**都不放宽匹配语义**（内容寻址的唯一性冲突、符号寻址的定位失败均显式报错） |
| AC-14 | **后端可替换**：替换符号扩展的内部后端（如自包含后端 ↔ LSP 后端）不改变工具名、参数与结果结构；精度等级随结果如实上报；外部后端缺失时自动降级且任务不受阻 |
| AC-15 | **读取后校验**：文件在读取后被外部改动（内容指纹变化），写入被拒绝并返回可诊断错误；重新读取后可正常写入。需有自动化断言 |
| AC-16 | **原语级策略**：策略可只拦某个原语（如拒绝 `symbol_rename`）而放行其他原语；拒绝行为结构化上报，且被拒操作不产生任何落盘。**不按改动规模设阈值、不做影响面拦截**；改动规模只如实上报（见 §1.2「判据优先于偏好」） |
| AC-17 | **压缩保真**：触发压缩后，"永不丢"内容（Bounty 正文与验收标准、工作区约定、写操作记录）仍存在于上下文中；结果文件（patch、变更文件清单、假设清单）不因压缩缺失任何已发生的改动 |
| AC-18 | **压缩可观测且可复现**：每次压缩产出 `context_compacted` 事件（携带层级与释放 token 量）；同一 session 记录两次投影生成的工作日志内容一致（零模型调用） |
| AC-19 | **通道断裂**：stdout 写失败（模拟下游关闭管道）时，进程记录原因并以退出码 1 终止，不静默继续（FR-10.4） |
| AC-20 | **交付形态**：任务分支上形成提交链（**结构完整点上的自动检查点 ＋ 收尾交付提交**——自动检查点不按轮产生），分支在启动阶段即可见于远端；**交付 = 分支 tip**；只允许 fast-forward 推送，冲突时拒绝并退出码 1，**绝不 force push**；附带 diff **排除会话材料目录** `.xhunter/<session_id>/`（不排除该目录以外的 `.xhunter/` 路径，如 `skills.draft/**`，见 AC-25） |
| AC-21 | **推送边界**：策略拒绝推送到非任务分支、拒绝改写已推送历史与删除分支（FR-8.3） |
| AC-22 | **检查点自愈与止损**：单次提交失败不中止任务（下一轮累积重提）；连续失败达上限 → 环境错误（退出码 1）。**自动检查点只落在结构完整点上**（FR-1.3d）：判据不可判定时不提交；收尾交付提交照常 |
| AC-23 | **AGENTS.md 规范**：根级 AGENTS.md 存在时全文注入 system 段且压缩后仍在（对齐 AC-17）；monorepo 嵌套场景下，模型读/写/编辑命中某文件后，其结果附注携带路径链上最近且未注入过的 AGENTS.md；文件名大小写不匹配（如 `agents.md`）不作为规范文件注入；运行中模型改动 AGENTS.md 不影响本次运行的注入内容（书写/生效分离） |
| AC-24 | **Skill 渐进加载**：启动时事件流含 skill 清单（仅 name+description）；模型未请求时 SKILL.md 全文**不出现**在上下文；`read` SKILL.md 走正常策略裁决与截断；模型写入 `.xhunter/skills/**` 被策略拒绝；非法 frontmatter 的 skill 被跳过且事件流可见；`scripts/` 无任何执行路径 |
| AC-25 | **书写/生效分离**：模型写入 `.xhunter/skills.draft/**` 被允许且进交付 diff；但该内容不出现在本次运行的发现清单中（激活面只认基线冻结版）；模型运行中修改 AGENTS.md 后，上下文中的项目约定与附注保持构造时内容不变 |
| AC-26 | **工具面恒定（同一构建内）**：**环境能力不决定注册**——扩展不具备引用解析能力 / 语言未注册 / 扩展不可用时，已接入的 `symbol_*` **仍然注册**（工具名与参数 schema 不变），调用返回结构化错误且**不降级为文本替换**；**工具面随能力接入而扩展**——尚未实现且不在本次构建范围内的原语（符号三原语随 MS-8 接入）**不注册**，落地后才纳入工具面；同一构建版本内工具名与参数 schema 不增减。注册规则见 §6 与 FR-4.11 |
| AC-27 | **协议与装配分离**：接一家**厂商**只需设置一组环境变量（协议、端点、鉴权头、模型上限）——协议实现、Harness 与组装层代码都不动；厂商特有差异（鉴权头的名称与前缀、端点约定）只体现在环境变量里；组装层没有该协议的适配器时**启动期**以退出码 1 失败并列出已装配的协议、指明该动哪里；协议实现里不出现协议取值的判断、不做注册、不依赖任何配置模型；Harness 侧不出现任何上游线格式类型（FR-16） |
| AC-28 | **响应异常不静默**：流在上游报错或未给结束标记时中断 → 显式 `error` 事件（带可重试性）；参数非法 / 工具名不认识 / 字段未知的调用 → 带结构化错误的失败结果回灌模型，`tool_result` 事件如实上报；两者都不得被当成"正常结束"或"调用成功"（FR-16.6） |
| AC-29 | **组装可扩展**：首轮 system / user 两段正文由插件贡献——同阶段多插件按装配顺序拼接（换顺序即换结果）、空正文的插件不留下空行、每段各只调用一次；内核条款（工具纪律、安全边界、无人类条款、止损规则）始终拼在 system 段末尾且插件无法删改；插件构造失败 → 退出码 1 且原因指明是哪一段；两段都不接插件时只记 warn、任务照常（FR-7.8、FR-7.9） |

**验收环境**：一期全部验收项（含 AC-6 的信号行为）在 **linux/amd64** 上执行；跨平台验收（Windows 信号等价物等）随 NFR-6 推迟到后续阶段。
